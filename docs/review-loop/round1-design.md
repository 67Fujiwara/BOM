# ラウンド1 設計者レビュー：flow-design.md（v1たたき台）

- レビュアー：全業界の電気設計者代表（自動車 / FA・産業機械 / 医療機器 / 半導体製造装置 / 民生電子 / 建築設備・プラント。制御盤・基板・ハーネスの電気設計とBOM作成を10年以上）
- 対象：`docs/flow-design.md` v1。`docs/keyboard-spec-v0.1.md` は採用決定済みとして前提に置く（流れとの整合で足りないキー・画面だけ指摘する）
- 方法：6シナリオを設計者の立場で実際にキーを打つつもりで歩き、「資料の作り直し」「聞き直し」「二度手間」「同じ指摘を二度受ける」「誰が決めるか不明で止まる」が起きる箇所を洗い出した

---

## 1. 業界ごとに特有の要求（流れに影響するものだけ）

- **自動車（車載ユニット・ハーネス）**：型式変更は必ずECN/設変番号と理由（客先要求 / 設計起因 / 廃番）を伴う。代替品は「同等品」ではなく再評価・再認定（PPAP/承認図）の対象。環境物質（IMDS/RoHS/REACH）の確認が購買指摘の定番で、型式の「あいまい」の大半はサフィックス（梱包・テープ・鉛フリー）違い。
- **FA / 産業機械（制御盤）**：BOM行は回路記号（デバイス番号 KM1・Q3・X10 …）と図面番号・盤番で図面と紐づく。客先指定メーカ（三菱/オムロン/キーエンス指定）と UL508A / CE 対応品が必須で、代替は **客先承認** が要る。予備品リスト・盤ごとの数量集計（員数×盤数）が購買提出の前提。
- **医療機器**：ISO 13485 の設計管理下で、変更はすべて履歴とレビュー記録が必要。承認済みベンダーリスト（AVL）外の商社・メーカは購買が勝手に選べない。IEC 60601 の安全関連部品（絶縁電源・ヒューズ・コネクタ）は代替で再検証が発生する。
- **半導体製造装置**：客先AVL・SEMI S2/F47 指定の部品が多く、真空部品・特殊ケーブルはリードタイムが長い（長納期部品の先行手配が日常）。社内仕様書番号（社内コード）と改版（Rev）で部品を管理し、型式だけでは一意に決まらない。見積有効期限の管理が重要。
- **民生電子（基板）**：行は Reference Designator（R1, C23 …）で数百行、同一型式は集約して発注数＝員数×基板枚数×予備率。EOL/PCN の監視と 2nd source（代替登録）が標準で、リール単位の MOQ・端数が購買指摘の定番。
- **建築設備 / プラント**：承認図・仕様書に対する客先（施主/ゼネコン）承認が必要で、メーカ変更は承認図の差し替えになる。JIS/防爆/耐候などの規格指定、客先支給品、現地調達、長期プロジェクトのため **見積有効期限切れ** が頻発する。

共通して流れに効くこと：①型式だけでなく「図面上の識別子（回路記号 / RefDes / 仕様書番号）」で行を特定したい、②代替品は「誰が承認するか」が業界で違う（設計だけでは閉じない）、③変更には理由・番号が付く、④見積には有効期限がある、⑤部品の必要日は案件納期ではなく工程から逆算する。

## 2. 手戻りが起きる箇所（BLOCKING）

### B1. v1 の保存先がブラウザ（IndexedDB）なので「同じ1つのBOMを3者が見る」が成立しない
- **シナリオ**：S1（すべてのシナリオの前提）
- **何が起きるか**：§1 は「コピーやExcelの往復はしない」と書くが、§9 は「保存はブラウザ（IndexedDB）+ JSONエクスポート。将来はサーバ同期」。v1 では設計のPCにしかBOMが無く、購買は見られない。結局 JSON か Excel を送り、購買の入力結果をまた取り込む往復になる。指摘・見積・採用・履歴のイベントログも PC ごとに分かれ、`Ctrl+Z` と履歴が整合しない。
- **修正案**：v1 の時点でサーバ同期（最低限、案件単位の共有ストア + イベントログ追記型）を前提にする。それが無理なら v1 の流れを正直に「ファイル往復」として書き直し、`案件を共有（JSON書き出し）` と `取り込み（差分マージ、行IDで突合）` のコマンドと、取り込み時の衝突表示（同じ行IDの同じセルを両者が変えた）を定義する。どちらにするかを未決のまま流れを描かない。

### B2. 「提出」の操作とキーが無い（状態遷移 下書き→提出済 を誰がいつ起こすか不明）
- **シナリオ**：S1、S5（追加行）
- **何が起きるか**：§2 の状態は「行ごと」なのに、提出は案件単位の行為。keyboard-spec にはパレット `提出として記録` と `Ctrl+E` しか無く、flow-design は「再提出ボタンは無い」と言う。設計は 80 行作った後、「提出済にするには何を押すのか」「購買にどう伝わるのか」が分からず、結局チャットで「出しました」と連絡する＝意思疎通の手戻り。
- **修正案**：
  - `Ctrl+Enter`（ナビ）= 「提出」。チェック済みで下書きの行をすべて「提出済」にし、提出スナップショットを取る（これが `5 変更あり` の「前回提出」の基準になる）。パレット名は `提出`（`提出として記録` を改名）。
  - 提出はエラー0が条件、警告は `x` 確認済みで可、`Shift+→ あとで` にした問題が残っていれば提出不可、とルールを明記する（7.1 手順7 の「あとで」が提出をブロックするかが今は不明）。
  - 行単位でも提出できるようにする（S5 の追加 2 行だけ出す）：行選択で `Ctrl+Enter`。
  - 提出した事実は購買の「受信箱」に出す（B3）。

### B3. 購買・PM が「自分宛ての仕事」を案件横断で見る画面が無い
- **シナリオ**：S1、S2、S4、S6
- **何が起きるか**：通知は「ヘッダーランプと件数のみ」だが、ランプは **開いている案件** のもの。購買は 10 案件を抱え、どの案件に新しい提出・対応済み・正式見積回答が来たか分からない。設計も「指摘がついたか」を案件を開いて回らないと分からない。結局メール／チャットで「見てください」と言う。
- **修正案**：`Ctrl+P` の案件一覧を「受信箱」に拡張する：案件ごとに「自分の役割宛ての未処理件数（提出待ち / 指摘未対応 / 要決定）」と最終更新者・時刻を列で出し、`Enter` で開いたら最初の未処理行に `n` 相当でジャンプ。既定ビューを役割で変える（設計=`4`、購買=`5`、PM=`7`）。日次ダイジェストは「送るなら」ではなく既定ONにし、対象は受信箱の差分だけにする。

### B4. 購買→設計の指摘を起票するキーが無く、設計→購買への質問経路も無い
- **シナリオ**：S2、S3、S4
- **何が起きるか**：§3 の Issue モデルは良いが、keyboard-spec に「指摘を付ける」キーが無い。さらに Issue は本文1本で返信が無い。型式あいまいに対して設計が「どの候補を想定？」と聞き返す、購買に「この商社は取扱あるか」と聞く、といった **逆方向の問い** はチャットに逃げる。同じ行について別経路で会話が発生し、記録が分散する。
- **修正案**：
  - ナビで `!` = 今のセルに指摘を起票（種別は頭文字で選択 → 本文 → `Enter`）。パレット `<ID> 指摘 <種別>`。
  - Issue に **スレッド返信**（`Space` で行を開いた中で指摘を選び `Enter` → 返信）と、種別に「質問（設計→購買）」「質問（購買→設計）」を追加。返信があるとき相手の受信箱（B3）に出す。
  - 「指摘を閉じる」の権限を定義：対応済 = 設計が直した、確認済 = **起票者** が閉じる、見送り = 起票者 or PM。設計側からは `x` で「対応済（変更なし・理由必須）」にできる（型式が正しくて商社カタログが古い場合など、セルを変えずに回答するため）。

### B5. 「直した瞬間に購買側に反映」だと、入力途中の行を購買が見て二重指摘が起きる
- **シナリオ**：S2、S5
- **何が起きるか**：12 件のうち 7 件直した段階で購買が見ると「残り 5 件まだですか」と聞かれる。型式を打ちかけのセル（`Enter` 前後で中途半端な値）や `Shift+Enter` で追加したばかりの空行が「変更あり」に出て、購買が「型式空欄」の指摘を付ける → 設計は同じことを二度やる。これは目標 (1) に正面から反する。
- **修正案**：行ごとに「作業中（設計ローカル）」と「公開済」を分ける。編集は作業中に積み、`Ctrl+Enter`（行 or 案件）で公開し、そのときに提出前チェックが走る。公開前の行は購買から「設計作業中 ●」のグレー表示のみ（値は見えない）。指摘の「対応済」は公開時に自動で付く。ステータスバーに「未公開 7 行」を常時表示。

### B6. 購買の「代替提案」を設計が受け入れる操作が無い（手打ちし直し）
- **シナリオ**：S2（廃番2）、S4（コスト超過の代替）、S6（納期の代替）
- **何が起きるか**：購買が指摘本文に代替型式を書く → 設計は `r` で置換行を作り、本文から型式・メーカを目で写して打つ。転記ミスと、元の行の指摘が宙に浮く（元の行は不採用になるが Issue は未対応のまま）。
- **修正案**：
  - 指摘種別「代替提案」「廃番」に構造化フィールド（提案型式・提案メーカ・提案商社・理由）を持たせ、`Ctrl+.` の候補に「提案を適用（`r` で置換行を作り、型式・メーカを入れる）」を出す。
  - `r` を指摘付きの行で押したら、指摘を新行に **引き継ぎ**、新行の型式確定で対応済に。元の行は「置換済（→R081）」の状態で残す。
  - 代替品の **承認者** を案件設定で持つ（設計のみ / PM / 客先承認要）。客先承認要の行は「代替承認待ち」フラグで提出・選定を止める（FA・プラント・医療は必須）。

### B7. 最小ロット指摘の決め方・決める人が無く、必要数と発注数が同じ列
- **シナリオ**：S2（最小ロット2）
- **何が起きるか**：購買「MOQ 100、必要 12」。設計は「数量を 100 に直すのか？」「型式を変えるのか？」「購買が端数購入先を探すのか？」が分からず聞き返す。数量を 100 に書き換えると、設計上の必要数が失われ、次の設変で「本当は 12 個」が分からなくなる。余剰コストの決定は本来 PM の予算の話。
- **修正案**：
  - 列を **必要数（設計）** と **発注数（購買）** に分ける。発注数は既定で必要数、商社の MOQ・入数で丸めた値を購買が入れる。差は「余剰」として金額に出す。
  - 指摘種別「最小ロット」に対する `Ctrl+.` 候補を固定する：①発注数を MOQ に（余剰金額を表示、閾値超なら要決定へ）、②型式変更（`r`）、③購買がバラ売り先を探す（指摘を購買に返す）。決定権：余剰が閾値以内は設計、超えたら PM。

### B8. 見積中の行の型式変更で、取得済み概算見積がどうなるか未定義
- **シナリオ**：S5（型式変更5行）
- **何が起きるか**：見積中の行の型式を設計が書き換えても、3 社の単価・納期はそのまま残り、スコアも古い型式のまま計算される。購買は気づかずに正式見積を依頼し、商社から「型式が違う」と戻る。正式見積依頼中の行なら、送付済みの依頼書との不一致になる。
- **修正案**：状態が「提出済」以降の行で 型式 / メーカ を変えたら、①既存の見積は「旧型式の見積」として履歴に残し無効化（グレー）、②状態を「提出済（再見積）」に戻し、③購買の受信箱に「再見積 5 行」、④正式見積依頼中なら「依頼書の差分版を再発行」コマンドを `Ctrl+K` に用意。変更は `Ctrl+Z` で戻せるが、公開後は履歴に残す。

### B9. 数量変更で見積が有効か無効か決まっていない
- **シナリオ**：S5（数量変更3行）
- **何が起きるか**：10 個→100 個で単価が変わる（数量スライド、MOQ をまたぐ）。設計は「見積は取り直しか」を購買に聞く。購買も商社に聞き直すか迷う。
- **修正案**：商社見積に「見積数量」を持たせ、発注数が見積数量から ±X%（案件設定、既定 20%）を超えるか MOQ をまたいだら「単価要確認」フラグ（スコアは保持、金額欄に注意色）、超えなければ有効。しきい値内でも購買が任意に再見積に回せる。

### B10. 提出後の行削除が物理削除になり、購買・商社への取消が伝わらない
- **シナリオ**：S5
- **何が起きるか**：keyboard-spec の `Shift+Delete` は行を消す。見積中の行を消すと、購買の「変更あり」に出ず、商社には依頼が残ったまま。
- **修正案**：提出済以降の行は `Shift+Delete` で「取消」状態（取り消し線で残す、金額集計から除外、変更点に「取消」として出る）。物理削除は下書きの行だけ。

### B11. 設計変更に「変更理由・変更番号」が付かない
- **シナリオ**：S5、S6
- **何が起きるか**：変更点は自動抽出されるが「なぜ」が無い。購買・PM は「客先要求か設計ミスか」でコスト負担と優先度を変えるので聞いてくる。自動車・医療・プラントでは ECN 番号なしの変更は受け付けられない。
- **修正案**：公開（`Ctrl+Enter`）時に、変更行があれば「変更理由（選択：客先要求 / 設計起因 / 廃番・入手難 / コスト / 納期 / その他）」と任意の変更番号を 1 回だけ聞く（行ごとではなく公開単位、行単位の上書きも可）。変更点シートと `5 変更あり` に列として出す。

### B12. 購買が見積を入れる手段が未決のまま流れに組み込まれている
- **シナリオ**：S3（設計が待たされる）、S4
- **何が起きるか**：3 社 × 80 行の単価・納期・MOQ・見積数量 = 約 1,000 セルを購買がどう入れるか未定（§10）。これが決まらないと「見積済」が来ず、設計の 2 営業日の選定期限も始まらない。手入力なら誤記で設計が気づいて聞き返す。
- **修正案**：`6 商社別` ビューを「商社ごとの入力シート」にして、商社見積 Excel からの複数セル貼り付け（型式で突合、行IDで突合、突合できない行は要確認）を v1 で確定。見積の単位（リードタイムは「日」に正規化、「即納」=0、「要確認」=未回答、「取扱なし」=辞退）をセルの選択肢で固定する。辞退と未回答は空欄と区別してスコアから除外する。

### B13. 納期スコアの基準が「案件納期」で、部品の必要日ではない
- **シナリオ**：S3、S6
- **何が起きるか**：部品は盤組立・基板実装・試験の前に要る。案件納期に対する余裕日数でスコアを付けると、納期ギリギリの商社が高得点になり、採用後に「組立に間に合わない」と判明して選び直す。
- **修正案**：案件設定に「社内工程日数（納期から逆算）」を持ち、**必要日 = 納期 − 工程日数** を既定、行ごとに上書き可（長納期部品の先行手配）。納期スコアと「納期NG」判定はこの必要日に対して行う。ヘッダーの「あと N 日」も必要日ベースを併記。

### B14. スコア2位以下を選ぶときの操作・理由・承認待ちの状態が無い
- **シナリオ**：S3
- **何が起きるか**：設計が `Shift+A` → `2` で在庫品の商社を選ぶ。RACI では「例外は PM が要決定ビューで決める」。選んだ瞬間に採用されるのか、PM が承認するまで止まるのか、理由をどこに書くのかが不明。PM は「なぜ 2 位？」と聞き、設計は口頭で説明する。
- **修正案**：`Shift+A` で最高スコア以外を選んだら、理由（選択：納期 / 在庫あり / 実績 / 集約 / 客先指定 / その他＋本文）を必須で聞き、状態を「選定済（PM承認待ち）」にして `7 要決定` に載せる。PM は要決定ビューで `y` 承認 / `Shift+Y` 差し戻し。スコア差が **拮抗しきい値（既定 5 点）以内** なら設計の裁量で承認不要（§6 の「スコア拮抗→PM」は逆で、拮抗は設計が決めてよい）。

### B15. 正式見積の差分しきい値と「超えたときの選択肢・戻し先」が無い
- **シナリオ**：S4
- **何が起きるか**：15% 高い 3 行が要決定に載る。PM の選択肢（受入 / 購買が再交渉 / 2 位商社に変更 / 設計が安い型式を検討）が画面に無く、会議になる。「設計で安い型式を」と決まっても設計への戻し方が無い。2 位商社に変えると概算の有効期限切れで再見積の二周目になる。
- **修正案**：
  - 閾値を案件設定（既定：±10% または ¥X の大きい方）にし、閾値内は自動で「正式見積済」。
  - 要決定行で PM が選ぶ対策を固定：①受入、②再交渉（購買へ、期限付き）、③商社変更（`Shift+A` 相当、概算の有効期限内のみ候補に出す）、④設計検討（種別「コスト超過」の指摘として設計の `4 要確認` へ）。
  - 商社見積に **有効期限** を持たせ、期限切れはスコア計算から外す。
  - ヘッダーに「合計金額 / 予算」を出す（PM は 3 行の 15% より全体の予算超過で判断する）。

### B16. 納期を変更する操作が無く、変更後の全体見直しの流れが無い
- **シナリオ**：S6
- **何が起きるか**：納期の入力は 7.1 の新規作成ガイドにしかない。PM が前倒しを決めても画面上で変えられず、口頭で伝えて設計が直す。変えたとしても、選定済・正式見積依頼中・発注済の行がどうなるかが未定義で、三者で会議して一行ずつ対策を決める。
- **修正案**：
  - `Ctrl+K` → `納期を変更`（PM のみ、理由必須）。変更前に **試算** を出す：新しい必要日で「納期NG」になる行数、状態別（未選定 / 選定済 / 依頼中 / 発注済）、特急費の概算。
  - 確定すると納期NG行に **対策区分** 列（空欄）を付けて `7 要決定` に載せ、PM が行ごと（または一括）に割り当てる：商社変更（購買）/ 代替品検討（設計、指摘種別「納期NG」で `4` へ）/ 分納・特急交渉（購買）/ 受入（遅延許容）。割り当てた瞬間に担当者の受信箱に出る。
  - 発注済の行は「回答納期」「入荷予定日」を持たせ（今は「納期」1 列のみ）、入荷予定日 > 必要日 の行を同じ要決定に載せる。

### B17. `a` の意味が keyboard-spec（最安）と flow-design（最高スコア）で食い違う
- **シナリオ**：S3
- **何が起きるか**：ステータスバー・パレット（`未採用を最安で一括採用`、`R034 を因幡で採用 ¥8,040 最安`）は最安、flow は最高スコア。設計が「最安で採用した」と思って提出し、購買から「納期スコアが…」と言われる、または逆。
- **修正案**：keyboard-spec 5.4 と §6 のパレット文言を「最高スコア」に改め、`Alt+A` = 最安で採用、一括も `最高スコアで一括採用` / `最安で一括採用` の 2 本にする。ステータスバーに採用根拠（「スコア 87 / 最安」）を出す。

### B18. BOM の列に、購買指摘を未然に防ぐ列が無い
- **シナリオ**：S1 → S2（型式あいまい5・メーカ未記入3 の半分はこれで消える）
- **何が起きるか**：表の列は ID 部品名 型式 メーカ 数量 採用 金額 納期 状態 だけ。回路記号/RefDes/図面番号（行の特定）、単位・入数（モード説明には出るが表に無い）、代替可否（可 / 同等品可 / 指定品 / 客先承認要）、客先指定メーカ、希望納期（行）、社内コード/仕様書番号、備考が無い。購買は必ず「代替品でいいですか」「この品名はどの図面のどこですか」と聞く。
- **修正案**：既定列に 回路記号（RefDes/デバイス番号）、図面番号、単位、入数、代替可否、客先指定、必要日（行上書き）、備考 を追加。`c` の列パネルで隠せるが、提出前チェックの既定ルールに「代替可否 未記入」「回路記号 重複」「同一型式で代替可否が不一致」を入れる。

## 3. あいまいで聞き直しが発生する箇所（AMBIGUOUS）

### A1. 状態遷移図と本文の矛盾（指摘で「下書き」に戻るのか、フラグだけなのか）
- **シナリオ**：S2
- **何が起きるか**：図は「指摘あり → 下書き」に矢印、本文は「状態ではなくフラグ」。設計は、直した後の行が見積中のままか提出済に戻るか分からず購買に聞く。
- **修正案**：フラグに統一し、図から戻り矢印を消す。ただし 型式 / メーカ 変更は B8 のとおり状態を「提出済（再見積）」に戻す、と例外を明記。

### A2. 「相見積先」を決めるのが設計（7.1 手順5）なのか購買（RACI）なのか
- **シナリオ**：S1、S3
- **何が起きるか**：設計が新規作成で 3 社選ぶが、購買が「この商社は取引停止」「AVL 外」と差し替える。設計は次の案件でまた聞く。
- **修正案**：7.1 手順5 は「希望商社（任意）」に改名し、確定は購買（商社マスタの「取引可 / AVL」フラグで選べない商社は候補に出さない）。送付先（手順4）は「購買担当者」と明記。

### A3. 役割の「商社を選ぶ（または選定案を承認する）」が二択のまま
- **シナリオ**：S3
- **何が起きるか**：案件によって購買が選定案を作るのか設計が選ぶのかが決まっておらず、互いに相手待ちで止まる。
- **修正案**：案件設定で「選定者：設計 / 購買」を 1 つ選ぶ。既定は設計（スコア順）、購買が選ぶ案件は設計が `7 要決定` 相当の画面で承認。

### A4. チェックルールの表現力（「型式あいまい」をルールにできるのか）
- **シナリオ**：S2
- **何が起きるか**：「ルールを追加」で再発ゼロと書くが、メーカ未記入は空欄チェックで済む一方、型式あいまいはメーカごとの型式の書式（正規表現・サフィックス必須）が無いとルール化できない。設計は追加しようとして何を書けばよいか分からない。
- **修正案**：ルールの種類を列挙する：必須、正規表現（メーカ別）、禁止文字（全角英数・前後空白）、マスタ照合（メーカ名の正規化辞書）、重複、数量と入数の整合。指摘種別ごとに「対応するルール種類」を `ルールを追加` のテンプレとして出す。ルールの適用範囲（全案件 / この案件）も聞く。

### A5. 要決定ビューに載せる「スコア拮抗」の定義とスコアの既定の扱い
- **シナリオ**：S3
- **何が起きるか**：拮抗の点差、同点のとき、新規商社の実績（過去データなし）の点数、未回答・辞退の商社の扱いが未定義。設計は `a` の結果が妥当か判断できず購買に聞く。
- **修正案**：拮抗 = 1 位と 2 位の差が 5 点以内（案件設定）。実績なしは 50 点（中立）と表示に「実績なし」を出す。未回答・辞退はスコア対象外。同点は納期 → 価格の順。

### A6. 正式見積依頼書に「選定理由（スコア内訳）」を付けると他社の価格水準が商社に漏れる
- **シナリオ**：S3 → 正式見積依頼
- **何が起きるか**：スコア内訳（価格 = 最安比）は相対値でも競合の値付けを推測させる。購買は「これは出せない」と設計に差し戻し、依頼書を作り直す。
- **修正案**：依頼書（社外）には 行・数量・希望納期・有効期限の要求 だけを載せ、選定理由は社内用の「選定記録（PDF）」として別に出す。パレットも `正式見積を依頼（社外）` と `選定記録を出力（社内）` に分ける。

### A7. 誰が操作したかを記録する「ユーザー」の概念が無い
- **シナリオ**：全部（起票者、変更履歴、RACI の期限）
- **何が起きるか**：イベントログは「誰が」を持つが、ログイン・役割の設定が無い。1 台の PC で購買が `a` を押せてしまい、「誰が採用したのか」で揉める。
- **修正案**：最低限、ユーザー名と役割（設計 / 購買 / PM）の設定を案件外で持ち、役割外の遷移キー（設計の `o`、購買の `a` など）はステータスバーで灰色表示＋パレットで「権限なし」と出す。

### A8. 期限（2 営業日・1 営業日）の起点と営業日カレンダー
- **シナリオ**：S3、S4
- **何が起きるか**：「見積済から」は全行が見積済になった時点か、行ごとか。営業日の定義（会社カレンダー）が無く、ヘッダーの「あと N 日」が暦日なのか営業日なのか。
- **修正案**：期限は行ごとに起算（行が見積済になった時刻）、ヘッダーには「期限超過 N 行」。営業日カレンダー（休日）を設定に持つ。

### A9. 「商社を集約」が試算だけで、適用する操作と集約時の選定例外の扱いが無い
- **シナリオ**：S3、S6
- **何が起きるか**：3 社に分散すると送料・発注手間が増える。試算を見て「集約したい」と思っても適用キーが無く、1 行の 2 位商社（S3）をどう扱うかも不明。
- **修正案**：試算画面で `Enter` = 適用（全行を 1 社に `Shift+A` 相当で付け替え、理由「集約」を自動記入、承認が要る行はまとめて要決定へ）。

### A10. 「要確認」ビューの `n` の順序が指摘の種別で揃っていない
- **シナリオ**：S2
- **何が起きるか**：12 件を行順に回ると、型式あいまい→メーカ未記入→廃番→型式あいまい… と思考が切り替わる。種別ごとに並べたい。
- **修正案**：`4 要確認` の既定の並びを「種別 → 行」にし、`s` で行順に切り替え可。ステータスバーに「型式あいまい 2/5」と残数を出す。

---

## 4. 良い点

- 指摘を「行ID + セル + 種別」の構造化データにし、直した瞬間に対応済になる設計は、目標 (1) の核心を正しく押さえている。
- 状態を行ごとに持ち、案件状態を集計で出す方針は、部分的な先行手配・分納の実務に合う。
- スコアの重みを案件ごとに持ち、内訳を `Space` で見せる透明性は、設計が「なぜこの商社か」を説明する手間を減らす。
- RACI を表にして期限の目安まで書いたのは良い。あとは画面に落とすだけ。
- `ルールを追加` で指摘を再発防止に回す発想は、業界をまたいで効く。
