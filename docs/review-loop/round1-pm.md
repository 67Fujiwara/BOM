# Round 1 レビュー：全業界PM（電気設計×購買の案件運営）

- レビュアー：全業界PM代表（自動車 / FA・産業機械 / 医療機器 / 半導体製造装置 / 民生電子 / 建築設備・プラント）
- 対象：`docs/flow-design.md`（v1 たたき台）
- 前提：`docs/keyboard-spec-v0.1.md` は採用決定。本レビューは否定せず、フロー設計側で整合を取ることを求める
- 評価軸：
  1. 購買の指摘で設計が直すコスト ≒ 0
  2. 設計・購買・PM の意思疎通による手戻り = 0
  3. **誰が・いつ・何を決めるかが画面で一目で分かり、止まっている箇所が即座に見える**

---

## 1. 業界ごとに特有の要求（フローに影響するもの）

- **自動車**：承認部品リスト（AVL）外のメーカ・商社への変更は顧客承認が要る。「2位商社を選ぶ」「代替品」は設計承認だけでは完結せず、変更管理（ECN）番号とひも付かないと監査で落ちる。
- **FA / 産業機械**：客先指定品（指定メーカ・指定型式）が BOM の 2〜3 割を占める。指定品に「型式あいまい」「代替提案」の指摘を出すこと自体が無駄なので、行に「指定品」属性が要る。装置納期直結なので納期は行単位で違う（先行手配品がある）。
- **医療機器**：ISO 13485 の設計管理。見積中の設計変更は「設計変更手続き（承認者・理由・影響評価）」を通さないと行えない。「直した瞬間に購買へ反映」は QMS 上そのままでは使えず、変更セットの承認ゲートが必要。
- **半導体製造装置**：リードタイム 20〜40 週の部品があり、正式見積を待たずに先行発注する判断（PM 決裁）が日常。ステートマシンが直列だと先行発注を表現できない。客先承認 BOM のため部品変更は設計承認者の記録必須。
- **民生電子**：コスト最優先で購買主導の VE（代替提案）が多く、EOL/PCN 管理が常時走る。予算（目標原価）に対する総額差分が案件単位で常に見えないと PM は判断できない。二次ソース（同一行に 2 メーカ）が普通。
- **建築設備 / プラント**：客先承認図で型式が固定され、メーカ変更は承認図の再提出（数週間）になる。支給品・客先指定商社の行があり、相見積の対象外行をフローから除外する必要がある。予算超過は PM の上（工事責任者）の決裁ルート。

共通して効くもの：**(a) 予算超過の決裁ルート（PM の上が居る）、(b) 変更管理（理由・承認者・番号）、(c) 先行発注の例外、(d) 相見積対象外の行（指定品・支給品）**。v1 はいずれも持っていない。

## 2. 手戻りが起きる箇所（BLOCKING）

各項目：シナリオ / 何が起きるか / 具体的な修正案

### B1. 「同じ 1 つの BOM を 3 者が見る」のに保存先がブラウザローカル（IndexedDB）
- シナリオ：S1（全シナリオの土台）
- 何が起きるか：設計の PC に保存された BOM を購買・PM は見られない。結果、JSON エクスポートをメールで回す＝「Excel 往復はしない」方針と矛盾する Excel 往復と同じ。v1 の目標 2・3 は成立しない。通知（ランプ）も自分の PC の中だけで点く。
- 修正案：v1 の範囲で **共有ストア（サーバ or 共有フォルダ上の単一 JSON + 排他）を必須**にする。「将来はサーバ同期」を「v1 から 1 案件 1 ストア、3 者同時参照」に改める。ログイン（氏名・役割）を持ち、イベントログの「誰が」を実データにする。これが無いと以下すべての通知・期限・RACI が机上になる。

### B2. 「提出」の操作とゲートが未定義（下書き → 提出済 の遷移キーが無い）
- シナリオ：S1
- 何が起きるか：keyboard-spec には `提出として記録` と `Ctrl+E 出力` があるが、flow-design の状態「提出済」にどの操作で入るのか、案件単位か行単位か、チェック NG が残っていても提出できるのかが書かれていない。設計は Excel を出して送るのか、記録だけなのか迷い、購買は「来たのか」が分からず聞き直す。
- 修正案：パレット `提出` （ショートカット `Shift+P` 相当、ナビモード）を定義。**行単位**で「下書き→提出済」、`2` ビューで選択中の行（または全行）を一括提出。ゲート：エラー（赤）が残る行は提出不可、警告（黄）は `x` 確認済みなら可。提出時に「提出 No.（#1, #2…）」を自動採番し、変更ありビュー `5` の基準点にする。

### B3. 購買担当・設計担当・PM が案件に割り当てられておらず「誰待ちか」が無い
- シナリオ：S1, S2, S3, S4（全部）
- 何が起きるか：ヘッダーには「エラー 4 / 警告 9」だけ。PM が開いても「今止まっているのは誰のボールか」が分からず、会議で確認する。
- 修正案：案件に **担当者 3 名（設計 / 購買 / PM）** をデータ項目として持つ。行ごとに **「次のアクション担当（ボール）」を状態から自動導出**して列表示（下書き→設計、提出済・見積中→購買、要決定→PM、指摘あり→設計…）。ヘッダーに「設計待ち 12 / 購買待ち 38 / PM 待ち 3」を常時表示し、`Ctrl+P` の案件一覧にも同じ 3 数字と「最古の待ち日数」を出す。

### B4. 期限が「目安」の文章だけで、データ項目・起点・超過表示が無い
- シナリオ：S2, S3, S4
- 何が起きるか：「見積済から 2 営業日」「回答から 1 営業日」の起点となるイベントが行に記録されない。期限超過の色変化を実装できず、PM は止まっている箇所を見つけられない。
- 修正案：行に `期限` 列（状態遷移時に RACI 表から自動計算、手動上書き可）と `待ち日数` 列を追加。超過は行の状態セルの色を変える。ビュー `7 要決定` に「期限超過」も含める。案件設定に「営業日カレンダー（休日）」を持つ。

### B5. 購買が指摘を起票する操作が無い
- シナリオ：S2
- 何が起きるか：指摘は「行 ID + セル」に付く構造化データと定義されているが、購買がどのキーで起票し種別を選ぶかが無い。購買はメールで 12 件書いて送る → 設計が手で転記 → 変更コストゼロが崩れる。
- 修正案：ナビモードでセル上 `Shift+I`（または パレット `指摘`）→ 種別を頭文字で選択（`k` 型式あいまい、`m` メーカ未記入、`d` 廃番、`l` 最小ロット、`a` 代替提案、`n` 納期 NG、`o` その他）→ 本文 → `Enter`。同じ種別を複数行に付ける `Shift+I` の連続起票（`J` で下へ）も用意。購買が 12 件を 2 分で打てることを受け入れ基準に入れる。

### B6. 「最小ロット」「廃番」「代替提案」の指摘は設計が直すものではなく **決定** が要るのに、設計に落ちる
- シナリオ：S2
- 何が起きるか：最小ロット 2 件は「数量をロットに合わせて余剰を持つ（コスト増）」か「端数で割高を受け入れる」かの判断で、設計には決められない（RACI では数量は設計だが、コスト影響は PM）。廃番 2 件は代替品の選定（設計）とその価格差の受入（PM）の 2 段階。設計が勝手に決めて後で PM に覆される、または設計が PM に聞きに行く。
- 修正案：指摘種別ごとに **解決担当（R）と承認者（A）** を定義表で持つ。最小ロット・納期 NG・代替提案のうちコスト影響が閾値超のものは、設計が対応した時点で自動的に `7 要決定`（PM）に入る。指摘に「回答（設計）」と「決定（PM）」の 2 欄を持つ。

### B7. 指摘に「設計側の回答」欄が無く、「見送り」を誰が決めるか不明
- シナリオ：S2（メーカ未記入 3 件のうち「相当品可」で型式確定しない場合）
- 何が起きるか：指摘の本文は起票者のみ。設計が「このままで良い理由」を書く場所が無く、口頭・メールで説明する。「見送り」状態に設計が勝手に遷移させられるなら購買は納得せず再起票、できないなら設計は止まる。
- 修正案：指摘に `回答` フィールドを追加（設計が `Enter` で直す代わりに `Shift+Enter` で「直さず回答」）。状態遷移の権限：未対応→対応済（設計）、対応済→確認済（購買）、対応済→未対応（購買、差し戻し。差し戻し理由必須）、見送り（起票者＝購買が確定、または PM）。差し戻し回数を行に表示し、2 回目以降は自動で `7 要決定` に上げる（往復を止める）。

### B8. 置換（`r`）で新行が生まれると、指摘が元行に残り、新行の指摘状態が宙に浮く
- シナリオ：S2（廃番 2 件）、S5
- 何が起きるか：廃番指摘は元行のセルに付く。`r` で元行は不採用、新行は下書き。元行の指摘は「対応済」にならず、新行には指摘が無い。購買の要確認件数が減らず、設計は「対応したのに赤が消えない」と聞き直す。
- 修正案：置換時に元行の指摘を自動で「対応済（置換 → R0xx）」にし、新行に「置換元 R0yy」のリンクを持たせる。変更ありビューで「R034 → R081（廃番置換）」として 1 行で表示する。

### B9. `a` の意味が keyboard-spec（最安）と flow-design（最高スコア）で食い違う
- シナリオ：S3, S6
- 何が起きるか：ステータスバーには「a 採用」としか出ず、設計は最安が採用されたと思い込む。`未採用を最安で一括採用` はスコアと無関係で、S6 の納期前倒し後に使うと納期 NG を大量に採用する。
- 修正案：keyboard-spec は採用決定なので `a` キーは変えず、**意味を「推奨（最高スコア）で採用」に統一**し、ステータスバー・パレット候補の文言を「a 推奨採用（因幡 ¥8,040 スコア 92）」に変える。一括コマンドは `未採用を推奨で一括採用` に改名し、`最安` 版は残すなら明示的に「（スコア無視）」を付ける。

### B10. スコア 2 位を選ぶ経路が未定義（設計が `Shift+A` で選べてしまう／選べない、どちらでも手戻り）
- シナリオ：S3
- 何が起きるか：RACI では「2 位以下を選ぶ＝PM が決める」。keyboard-spec の `Shift+A` → `1〜9` でそのまま採用できるなら RACI 違反で後から PM に覆される。採用できないなら設計は PM に理由を伝える手段が無く、会議になる。
- 修正案：`Shift+A` で 2 位以下を選んだ瞬間に **「例外選定の理由」入力（理由コード：在庫即納 / 客先指定 / 実績 / 品質 / その他 + 一言）** を必須にし、状態は「選定済（PM 承認待ち）」で `7 要決定` に入る。PM は `7` ビューで `J` `K` 移動しながら `y` 承認 / `n` 却下（却下理由必須）で 1 行ずつ処理。却下は「見積済」に戻し、設計のボールに戻る。

### B11. PM の「要決定」ビューに決定キーが無く、決定内容・決定者・日時がデータに残らない
- シナリオ：S3, S4, S6
- 何が起きるか：`7 要決定` に行が並ぶが、PM が何を押せば決定になるか、決定したことが設計・購買にどう見えるかが無い。PM は結局メールで「OK」と書き、購買が手で状態を変える。
- 修正案：`7` ビュー専用のナビ操作：`y` 承認、`n` 却下、`Shift+Enter` コメント付き承認。決定は **イベント「決定」（種別・決定者・日時・理由）** として行に残し、行を `Space` で開くと指摘・相見積と並べて表示。ヘッダーの「要決定 n 件」は PM 本人のときだけ強調。

### B12. 正式見積の「差分超過」閾値、超過時の選択肢と戻り先の状態が未定義
- シナリオ：S4
- 何が起きるか：15% 高い 3 行が `7` に飛ぶとして、PM の選択肢は (1) 受入、(2) 2 位商社に切替、(3) 設計に代替依頼、(4) 数量見直し。どれを選ぶとどの状態・誰のボールに戻るかが無い。購買は「どうしますか」とメールする。
- 修正案：案件設定に `差分閾値`（既定 ±10%、金額下限も）を持ち、PM が設定。`7` で該当行に対し `y` 受入（正式見積済へ）、`2` 2 位商社へ再依頼（選定済へ戻り購買のボール）、`d` 設計へ代替依頼（指摘種別「代替提案」を自動起票し設計のボール）、`q` 数量見直し（指摘種別「最小ロット」を自動起票）。各操作後の状態と担当を状態遷移表に明記する。

### B13. 案件単位の予算・概算総額・正式総額がヘッダーに無く、PM が行単位の 15% を判断できない
- シナリオ：S4, S6
- 何が起きるか：3 行が 15% 高くても他の行が安ければ案件総額は収まる。PM は Excel で集計し直してから判断する（資料作り直し）。
- 修正案：案件に `予算（目標原価）` を持ち、ヘッダーに「概算 ¥X / 正式 ¥Y / 予算 ¥Z（差 +n%）」と「納期 あと n 日」を常時表示。予算超過が閾値を超えた時点で案件レベルの `要決定` 項目（行ではない）を `7` ビューの先頭に出す。

### B14. 予算超過・納期 NG の決裁が PM の上（部門長・工事責任者・顧客）に行く場合の記録場所が無い
- シナリオ：S4, S6（自動車・医療・プラントでは必須）
- 何が起きるか：ツール外で決裁を取り、結果は口頭。後日「誰が承認したのか」で監査・顧客対応に手戻り。
- 修正案：決定イベントに `承認者（ツール外）` `承認日` `根拠（決裁書 No. / ECN No. / メール件名）` の自由項目を持たせ、PM が `7` で承認する際に入力できる。Excel 出力の「変更点」シートにこの列を含める。

### B15. 見積中・正式見積依頼中の行を設計が変更したときの状態遷移が未定義（ロック無し）
- シナリオ：S5
- 何が起きるか：ステートマシンの戻り線は「指摘あり」起点のみ。設計起点の型式変更 5 行・数量変更 3 行が「見積中」のまま値だけ変わると、購買は変更に気付かず古い型式で正式見積を取る。気付いても状態をどこに戻すか分からない。
- 修正案：提出済以降の行を設計が編集すると、**自動で「変更あり（再見積要）」フラグ**が付き、状態は「提出済」に戻る（イベントログに旧値→新値）。正式見積依頼中の行なら、依頼書の該当行を「取下げ」として再発行対象に自動マークする。変更は `Ctrl+Z` で戻せる。

### B16. 「直した瞬間に反映・再提出ボタン無し」は指摘対応には良いが、設計起点の変更 10 行をバラバラに購買へ流す
- シナリオ：S5
- 何が起きるか：設計が 10 行を 30 分かけて直す間、購買側では 1 行ずつ変更が出て商社に 10 回連絡する、または途中の中途半端な状態で再見積を出す。「まとめて送って」と購買が言い、設計はどこまでが 1 セットか説明する。
- 修正案：指摘対応（`4` ビューから `Enter` / `Ctrl+.`）は即時反映のまま。**設計起点の変更は「変更セット」**として扱う：提出済以降の行を編集すると変更セット（下書き）に溜まり、`提出`（B2）で「変更セット #3：型式 5 / 数量 3 / 追加 2」として一括で購買に出る。変更セットに `理由`（1 行必須、ECN 番号任意）を持つ。これが医療・自動車の変更管理の最小形になる。

### B17. 追加行（新規 2 行）の提出が案件全体の再提出と区別できない
- シナリオ：S5
- 何が起きるか：提出が案件単位だと 80 行すべてが「提出済 #2」になり、購買は「全部再見積か」と聞き直す。
- 修正案：B2 の行単位提出 + B16 の変更セットで解決。変更ありビュー `5` は「前回提出との差分」ではなく「変更セット単位」で切り替えられるようにする（`5` を押すごとに最新→1 つ前）。

### B18. 案件納期の変更操作・権限が無く、変更するとスコアが全行で再計算され選定済が覆る
- シナリオ：S6
- 何が起きるか：PM が納期を前倒しすると納期 30 点の配分が変わり、選定済 60 行のうち何行かで 1 位が入れ替わる。再採用するのか固定なのか決まっておらず、設計は全行を見直す（二度手間）。
- 修正案：案件納期・重みは **PM だけが変更可**（パレット `案件設定`）。変更時に「影響試算」パネル：納期 NG になる行 n 件、推奨が変わる行 m 件、総額差 ¥d を表示してから確定。**選定済の行はスコアをスナップショットで固定**し、「推奨が変わった」行だけ `7 要決定` に「再選定提案」として出す。PM が `y` で再選定（設計のボールへ）/ `n` で現状維持。

### B19. 長納期品の先行発注（正式見積前の発注）を直列ステートマシンが許さない
- シナリオ：S6（半導体製造装置・FA では必須）
- 何が起きるか：前倒し後、リードタイム 30 週の 3 行は正式見積を待てない。ツール上は発注済にできず、Excel で別管理になる。
- 修正案：PM 決定イベント「先行発注許可」を定義し、状態「見積済」または「選定済」から直接「発注済」に遷移できる例外経路を追加（決定イベントが無いと遷移不可）。行に「先行発注」バッジ。

### B20. 相見積先（商社）を設計が新規作成ガイドで決めてしまう
- シナリオ：S1, S3
- 何が起きるか：keyboard-spec 7.1 手順 5 で設計が相見積先を選ぶが、商社選定は購買の責任。購買が「この商社は使えない／あと 1 社足す」と差し戻す。
- 修正案：ガイドの手順 5 は「相見積先（購買が後で確定）」として既定値（購買マスタの推奨 3 社）を入れておく。購買は `6 商社別` ビューで商社の追加・除外ができ、変更は変更ありビューに出ない（設計に関係ないため）。RACI に「相見積先の確定：購買」を追加。

### B21. 相見積の対象外行（客先指定品・支給品・指定商社）を表す属性が無い
- シナリオ：S1, S2, S3
- 何が起きるか：指定品に購買が「型式あいまい」「代替提案」を出し、設計が「指定なので変えられません」と返す往復。スコア選定も指定商社で固定のはず。
- 修正案：行に `調達区分`（相見積 / 客先指定品 / 指定商社 / 支給品 / 社内在庫）を持つ（keyboard-spec の「調達区分」セルに既にある → 値を定義）。指定品・支給品の行は指摘種別「代替提案」「型式あいまい」を起票不可、スコア選定をスキップし状態「選定済（固定）」で進む。

### B22. 3 社中 1 社未回答で「見積済」になるのか、選定期限の起点はいつか
- シナリオ：S3
- 何が起きるか：2 社回答で設計が選定してしまい、3 社目の回答が後から来て覆る。または設計は待ち続け、期限超過が誰のせいか分からない。
- 修正案：行の状態「見積中」に「回答 2/3」サブ表示。案件設定に「見積回答期限」を持ち、期限を過ぎたら未回答商社を自動除外して「見積済」にする（購買が `6` ビューで延長可）。「見積済」になった日時を行に記録し、選定期限の起点にする。

## 3. あいまいで聞き直しが発生する箇所（AMBIGUOUS）

### A1. 「要確認」「要決定」の件数が自分向けか全体向けか
- シナリオ：全部
- 何が起きるか：ヘッダーの数字が「自分のボール」なのか案件全体なのか分からず、PM が設計の指摘件数を見て催促する。
- 修正案：ヘッダーは「自分の待ち n 件 / 全体 m 件」の 2 段。ログインした役割で切り替える（B1 前提）。

### A2. 「スコア拮抗」の閾値
- シナリオ：S3
- 何が起きるか：何点差で `7 要決定` に入るかが無く、設計は「これは PM 案件か」を毎回聞く。
- 修正案：案件設定 `拮抗閾値`（既定 5 点）。1 位と 2 位の差が閾値以下なら自動で `7` に入り、設計は `a` で仮採用のみ。

### A3. スコアの重みを誰がいつ確定するか
- シナリオ：S3, S6
- 何が起きるか：見積後に重みを変えるとスコアが変わり、選定が後出しで覆る。
- 修正案：重みは提出時に PM が確定（既定値のまま可）し、以後の変更は B18 の影響試算を通す。重みの変更はイベントログに残す。

### A4. 「在庫即納」をスコアにどう入れるか
- シナリオ：S3
- 何が起きるか：商社ごとの保持項目は 単価 / 納期 / 最小ロット / 備考 のみ。購買が「在庫あり」を備考に書くとスコアに乗らず、設計は 2 位商社を例外で選ぶことになる（本来なら 1 位）。
- 修正案：商社ごとの項目に `納期（日）` と `在庫区分`（在庫 / 取寄 / 受注生産）を持ち、納期スコアは `納期（日）` で計算。備考に頼らない。

### A5. 購買が指摘を「確認済」にするキー
- シナリオ：S2
- 何が起きるか：設計が直す → 対応済。購買が確認してクローズする操作が無く、「対応済」が溜まったまま。
- 修正案：`5 変更あり` ビューで `x`（警告の確認済みと同じキー）を「指摘を確認済にする」に流用。差し戻しは `Shift+X`（理由必須）。

### A6. 変更ありビュー `5` の基準点（「前回提出」とは何か）
- シナリオ：S2, S5
- 何が起きるか：指摘対応の変更と設計起点の変更が同じ差分に混ざり、購買は「どれが指摘対応でどれが設変か」を聞く。
- 修正案：差分に `起因`（指摘対応 R0xx-k / 変更セット #n）列を持つ。B16 の変更セットと連動。

### A7. 正式見積依頼書の再発行単位
- シナリオ：S4, S5
- 何が起きるか：依頼書は「商社ごとにまとめて」生成。3 行だけ再依頼・5 行だけ変更の場合、再発行は差分だけか全行か。商社は「前回と何が違うか」を聞く。
- 修正案：依頼書に `依頼 No.`（商社 × 連番）と「前回依頼からの差分」シートを自動で付ける。行単位で `依頼 No.` を記録。

### A8. 指摘の対応期限と、指摘が「止まっている」判定
- シナリオ：S2
- 何が起きるか：RACI の期限は「提出前」で、指摘対応の期限は無い。PM は「12 件のうち 3 件が 5 日止まっている」ことを見られない。
- 修正案：指摘種別ごとに既定期限（例：型式あいまい 1 営業日、廃番 3 営業日）。B4 の `待ち日数` を指摘にも持つ。

### A9. ルール追加のオーナーと衝突
- シナリオ：S2
- 何が起きるか：「ルールは全案件共通」で誰でも追加できると、設計と購買が互いに矛盾するルールを作り、提出前チェックが通らない／指摘が止まらない。
- 修正案：ルールに `作成者` `適用範囲（全案件 / この案件）` `有効/無効` を持ち、全案件共通への昇格は購買（チェックの受益者）が行う。

### A10. 納期 NG の判定基準
- シナリオ：S6
- 何が起きるか：「商社納期 > 案件納期」なのか「余裕日数（受入検査・組立）を引いた日」なのか不明。前倒し後に何行が NG かで設計と購買の数が合わない。
- 修正案：案件設定に `必要納期 = 案件納期 − 余裕日数（既定 10 営業日）` を持ち、行単位の上書き（先行手配品）も可。

### A11. 「見送り」「却下」した指摘・決定が将来の提出で再発しないか
- シナリオ：S2, S3
- 何が起きるか：見送りにした「メーカ未記入（相当品可）」が次の提出でまた指摘される。
- 修正案：見送りの指摘はその行・セルに「見送り済（理由）」として残し、同種別の再起票時に警告する。

### A12. 同時編集の扱い（未決事項のまま）
- シナリオ：S2, S5
- 何が起きるか：設計が型式を直している最中に購買が同じ行に金額を入れ、どちらかが消える。
- 修正案：v1 は **列単位の権限**で回避する：設計が書ける列（部品名・型式・メーカ・数量・調達区分）と購買が書ける列（商社別単価・納期・最小ロット・状態の見積系）を分け、行単位ではなく列単位で排他する。PM は決定イベントのみ。

### A13. 日次ダイジェスト（メール）を送るのか
- シナリオ：全部
- 何が起きるか：ランプだけだと案件を開かない限り気付かない。設計は週 1 回しか開かず、購買は電話する。
- 修正案：v1 で **「自分のボールが増えた日に 1 通」の日次ダイジェスト**を確定する（送信は PM が案件設定で ON/OFF）。メール本文は「設計待ち 3 行（R012, R034, R061）/ 期限超過 1」程度。

### A14. Excel 出力の役割
- シナリオ：S1
- 何が起きるか：keyboard-spec 7.2 の手順 4 は「出力」で終わるため、設計は出力して送るのが提出だと思う。
- 修正案：flow-design に「Excel 出力は社外（商社）・保管用。社内の提出は B2 の `提出` 操作」と明記し、keyboard-spec 7.2 手順 4 の読み替えを注記する。

## 4. 良い点（短く）

- 指摘を「行 ID + セル」の構造化データにし、直した瞬間に反映・差分自動抽出・ルール化で再発ゼロを狙う設計は、目標 (1) の芯を正しく捉えている。
- 行単位の状態と「指摘あり」をフラグに分けたのは正しい。案件全体を行の集計で見る発想も PM 向き。
- スコアを透明な加重平均にし、内訳と選定理由を依頼書に自動添付する点は、購買が商社に説明する手間と「なぜその商社か」の社内説明を同時に消す。
- 通知を「ランプと件数」に絞り、アニメ禁止設定に従う色変化で期限超過を出す方針は、現場の受け取り方として適切。
- RACI 表を設計書に置いたこと自体が良い。あとはそれをデータ項目と画面に落とすだけ。
