# レビュー Round 1：購買の立場から（全業界）

- 対象：`docs/flow-design.md` v1 たたき台
- 前提：`docs/keyboard-spec-v0.1.md` は採用済み。本レビューでは否定しない（ただし flow-design との**矛盾**は指摘する）
- レビュアー：自動車 / FA・産業機械 / 医療機器 / 半導体製造装置 / 民生電子 / 建築設備・プラント の電気部品購買（相見積・商社選定・正式見積依頼）10年以上の立場
- 方法：6シナリオを購買として実際に画面を操作するつもりで歩き、「資料の作り直し」「聞き直し」「二度手間」「誰が決めるか不明で止まる」が起きる箇所をすべて列挙した

---

## 1. 業界ごとに特有の要求（流れに影響するもの）

- **自動車**：承認メーカリスト（AVL）外のメーカ・代替品は設計変更扱いで PPAP/IMDS が必要。「購買が代替提案 → 設計が直す」は軽い操作ではなく、**承認者（品証・顧客）が流れに入る**。商社選定も「設計が選ぶ」は通らず、購買＋品証のサプライヤ評価が前提。
- **FA / 産業機械**：多品種少量で納期最優先。**在庫品（即納）かどうか**が商社選定の最大要因で、単価差より在庫の有無が勝つ。行ごとに「納期優先/価格優先」が違う。
- **医療機器**：ISO 13485 のため **設計変更（型式変更・代替品）は変更管理記録が必須**。誰がいつ承認したかが行単位で残らないと監査で止まる。ロット/シリアルのトレーサビリティのため入荷時にロット記録が要る。
- **半導体製造装置**：長納期部品（20〜40週）が混在し、**正式見積の前に先行手配（LTB）判断**が入る。顧客指定部品（SEMI S2 等の認証済み）は相見積対象外。高額部品は単品で予算承認。
- **民生電子**：MOQ・リール単位・価格ブレークが支配的。数量変更＝単価変更。EOL が早く**廃番指摘に代替型式がセットで付く**のが通常。セカンドソース（同等品複数登録）が前提。
- **建築設備 / プラント**：メーカが**仕様書で客先指定**されており購買が変えられない。承認図提出、分納・現場直送、年単位の工期で**納期は「必要日」が工程ごとに違う**。見積有効期限管理が重要。

→ 共通して流れに効くのは：(a) **行ごとの「メーカ指定の強さ」と「代替可否」**、(b) **行ごとの「必要日」**、(c) **代替提案は型式データで返す**、(d) **変更の承認記録**、(e) **商社選定の責任は業界で変わる**。flow-design v1 はこの5点をいずれもデータ項目として持っていない。

## 2. 手戻りが起きる箇所（BLOCKING）

### B-01 「同じ1つのBOMを3者が見る」が、保存がブラウザ（IndexedDB）では成立しない
- **シナリオ**：S1〜S6 すべて
- **何が起きるか**：§1「コピーや Excel の往復はしない」と §9「保存はブラウザ（IndexedDB）+ JSON エクスポート」が矛盾する。設計の PC で作った BOM を購買が見るには JSON を渡すしかなく、これは Excel 往復と同じ二度手間。購買が指摘を入れた JSON を設計に戻し、設計が直している間に購買が見積を入れると**マージ不能**。目標2・3が v1 で根本的に達成できない。
- **修正案**：v1 の時点で**共有ストア（最低限：共有フォルダ上の案件単位 JSON ＋ 行ごとのイベントログ追記型マージ、推奨：サーバ同期）**を必須とする。イベントログに `actor`（設計/購買/PM＋ユーザ名）`row_id` `cell` `before` `after` `ts` を持たせ、**行×セル単位で後勝ちではなく「担当者の責任セルは担当者しか書けない」**ロック（設計：型式/メーカ/数量/調達区分、購買：商社・単価・納期・正式見積、PM：決定）にする。これで未決事項3（同時編集）も解消する。

### B-02 購買用の画面・入口が無い（「購買」ビューが存在せず、新規提出を知る手段も無い）
- **シナリオ**：S1
- **何が起きるか**：§1 で購買は「同じ BOM 表の『購買』ビュー」を見るとあるが、§6 のビュー一覧に「購買」ビューは無い。購買は複数案件を同時に抱えるが、通知は「ヘッダーランプ（要確認・要決定の件数）」だけで、**どの案件が新規に提出されたか**を知るには `Ctrl+P` で案件名を当てずっぽうに検索するしかない。設計がメール/口頭で「出しました」と言う → 目標3違反。
- **修正案**：
  - 案件一覧画面（`Ctrl+P` を開いた状態）に **役割別インボックス**：「あなた宛（購買）：提出済 3件 / 対応済の指摘 12件 / 正式見積回答待ち 2件」。列：案件ID・案件名・納期・提出Rev・自分の未処理件数・最終更新者/日時。`Enter` で開く。
  - ビューに **「9 購買作業」** を追加：状態＝提出済/見積中/見積済の行だけ、列＝ID・部品名・型式・メーカ・数量・単位・入数・調達区分・指定強さ・必要日・商社1〜n（単価/納期/MOQ/在庫）。

### B-03 「提出」の操作と単位（Rev）が定義されていない
- **シナリオ**：S1、S5
- **何が起きるか**：keyboard-spec にあるのは「提出として記録」というパレットコマンドだけ。§2 の状態「下書き→提出済」が**全行一括なのか選択行なのか**不明。S5 で追加2行だけ提出したいとき、「提出として記録」が全行を再提出扱いにすると、購買側の「5 変更あり」に見積中の78行まで差分として混ざる。購買は「どれが本当に見てほしい行か」を聞き直す。
- **修正案**：
  - 「提出」を **Rev 付きイベント**にする：`Ctrl+K → 提出 Rev.n`。対象は「下書き状態の全行」（既定）または選択行。提出時に案件ヘッダーに `提出 Rev.3（2026-10-22 設計:山田 → 購買:佐藤, 2行追加, 5行型式変更）` が残る。
  - 「5 変更あり」の基準点を **Rev 単位**にし、購買が `x`（確認済）した行は次の Rev の差分から消える。ビュー左に `Rev.2→Rev.3` のセレクタを置き `[` `]` で切替。
  - 提出時の**設計側ゲート**：チェックのエラーが残る行は提出できない（警告は `x` 確認済なら可）。これで購買の指摘のうち「型式あいまい」「メーカ未記入」の大半を提出前に止める（目標2）。

### B-04 購買が相見積を取るために必要なデータ項目が行に無い
- **シナリオ**：S1（提出直後に購買が設計へ聞き直す）
- **何が起きるか**：画面の列は ID・部品名・型式・メーカ・数量・採用・金額・納期・状態。購買が商社に概算見積依頼を出すには最低限 **単位、入数、調達区分（購入/支給/客先指定）、メーカ指定の強さ、代替可否、必要日、製品台数（数量の根拠）、規格要求** が要る。無いと 80行中 20〜30行は「これは客先指定ですか？」「同等品で良いですか？」「数量は10台分ですか？」と聞き直す。S2 の「型式あいまい5件」「メーカ未記入3件」のうち半分はこの項目が無いことが原因で発生している。
- **修正案**：行データ項目を追加（すべて `c` 列パネルで表示切替、既定で「購買提出用」ビューに表示）：
  - `unit`（単位）, `pack_qty`（入数）, `proc_type`（購入/支給/客先指定/社内在庫）
  - `mfr_lock`（メーカ指定の強さ：指定/推奨/任意）, `alt_ok`（同等品可/不可）, `alt_models[]`（設計が認める同等品の型式・メーカ）
  - `need_date`（行ごとの必要日。空なら案件納期を継承）
  - `qty_per_unit` × `units`（員数×台数）＋ `spare_qty`（予備）→ `qty` は計算値
  - `compliance`（RoHS/UL/CE/IMDS などのタグ）
  - 案件ヘッダーに `units`（製品台数）, `currency`, `budget`（予算、B-14 参照）
  - 「メーカ未記入」は **提出前チェックの既定ルール（エラー）** にし、提出をブロック。

### B-05 相見積先（商社）を設計が選ぶ構造になっている
- **シナリオ**：S1、S3
- **何が起きるか**：keyboard-spec 7.1 の新規 BOM ガイド step 5 で**設計が**相見積先を選ぶ。商社選定・相見積先の決定は購買の責任（自動車・医療ではサプライヤ評価が必須）。設計が選んだ3社のうち1社が該当メーカの取扱無し → 購買が差し替え → 設計の「選定」前提が崩れる。
- **修正案**：
  - step 5 は「相見積先（購買が後で確定。空のままでも次へ）」とし、**購買側で `Ctrl+K → 相見積先を設定`** を正とする。
  - 商社マスタに `handled_mfrs[]`（取扱メーカ）を持ち、行のメーカから**依頼可能な商社を自動で絞り込む**。取扱外の商社には依頼書を出さない（出すなら警告）。
  - メーカ直販を商社マスタの一種として扱う（`type: 直販/商社`）。

### B-06 購買が指摘を起票するキー操作・画面が無い
- **シナリオ**：S2
- **何が起きるか**：§3 で指摘は構造化データと定義されているが、keyboard-spec 5.5 のチェック系キー（`n` `x` `Ctrl+.`）はすべて**設計が直す側**の操作。購買が「このセルに型式あいまい」と付けるキーが無い。結果、購買はメールか Excel のコメントで指摘し、設計が転記する → 目標2違反。
- **修正案**：
  - ナビモードで `Shift+I`（Issue）：今のセルに指摘を付ける。小パネルが開き `1`〜`7` で種別、本文入力、`Enter` で起票。`Ctrl+Enter` で「代替提案」に型式・メーカ・商社・単価を構造化入力（B-07）。
  - 「4 要確認」ビューに**起票者フィルタ**（購買起票 / チェックNG）を付け、`f` で絞り込める。
  - 指摘一覧パネル `Shift+I` 長押しではなく `Ctrl+Shift+I`：案件の全指摘を種別・状態別に一覧、`Enter` でその行へ。

### B-07 指摘の起票タイミング（下書き/発行）が無く、12件を起票している途中で設計が直し始める
- **シナリオ**：S2
- **何が起きるか**：「直した瞬間に購買側に反映」は良いが逆向きが無い。購買が80行を順に見て12件起票する間（30〜60分）、5件目を起票した時点で設計が `n` で飛んで直し始め、その間に購買が付ける残り7件は**直された後の型式**に対して付く。設計は「どっちの型式に対する指摘か」を聞き直す。
- **修正案**：指摘に `draft/published` を持ち、`Shift+I` で起票した指摘は下書き。`Ctrl+K → 指摘を発行（n件）` で一括発行し、発行時点の行スナップショット（Rev）に紐づける。設計側の「4 要確認」には発行済だけが出る。発行後の追加は1件ずつ即発行でも良い。

### B-08 「廃番」「代替提案」指摘に型式データが付かず、設計が転記する
- **シナリオ**：S2（廃番2件）
- **何が起きるか**：指摘は「種別＋本文」のみ。購買は廃番と同時に「後継は XXX-B、同価格、A社在庫あり」を持っている。本文に書くと設計が `r` で置換行を作り、型式・メーカを**手で打ち直す** → 誤記のリスクと二度手間。さらに `r` は元の行を「不採用」にして新 ID の行を作るので、**元の行に付いた指摘・商社見積が新行に引き継がれない**（B-09）。
- **修正案**：
  - 指摘データに `proposal{model, mfr, vendor, unit_price, lead_time, moq}` を持たせる。
  - 設計側で `Ctrl+.`（その場で直す）の候補の先頭に「購買の提案 XXX-B を採用して置換」を出し、`Enter` で型式・メーカが入った置換行が作られ、`proposal` の商社見積がそのまま新行の相見積に転記される。
  - 医療・自動車向けに置換行に `change_reason`（廃番/コスト/納期/品質）と `approved_by` を残す。

### B-09 `r`（置き換え）で行 ID が変わり、指摘・相見積・状態が引き継がれない
- **シナリオ**：S2、S5
- **何が起きるか**：§9「行 ID 固定」は正しいが、置換で新 R0xx が生まれる。元の行は「不採用」、新行は「下書き」。元の行に3社の概算見積と指摘が付いたままで、新行には何も無い。購買は新行に対して再び相見積を取り直すが、**型式がマイナーチェンジだけ（サフィックス追加）の場合は再見積不要**なのに区別できない。
- **修正案**：
  - 「型式修正」（同一行 ID、`Enter` で編集）と「置換」（`r`、新 ID）を明確に分け、どちらでも**変更前後の型式が変更点として残る**。
  - 置換時に `supersedes: R034` を新行に持ち、元の行の指摘・相見積・状態を**コピーして「要再確認」フラグ**を付ける。購買は「5 変更あり」で `Enter` → 「再見積不要（価格据え置き）」/「再見積する」を1キーで選ぶ。

### B-10 購買の指摘に対する「対応済→確認済」「見送り」と、設計からの返答の操作が無い
- **シナリオ**：S2
- **何が起きるか**：設計が直すと自動で「対応済」。しかし (a) 設計が「このままで良い（サフィックスは任意）」と**返したい**とき、「見送り」を誰がどのキーで付けるか無い。(b) 購買が「対応済」を見て「確認済」にするキーが無い（`x` は設計のチェック警告用）。(c) 指摘に返信（スレッド）が無いので「どの部分があいまい？」の質問はメールに流れる。
- **修正案**：
  - 指摘パネル（行を `Space` で開いた下段）に `reply` を持ち、`Shift+R` で返信。返信者の役割を自動記録。
  - 設計側：指摘セルで `Shift+X` → 「見送り（理由必須）」。購買に「見送り 要確認」として戻る。
  - 購買側：「5 変更あり」の行で `x` → 「確認済」（警告の確認済と同じキーで良いが、ステータスバーに「指摘を確認済にする」と表示）。
  - 「最小ロット」指摘は設計が直すものではないことが多い（購買が端数を丸める）。種別ごとに**既定の担当**を持つ：型式あいまい/メーカ未記入/廃番 → 設計、最小ロット/納期NG → 購買が起案し設計は「数量変更可否」だけ答える。

### B-11 型式・数量を変えた行の見積状態が変わらず、商社への再見積が自動で発生しない
- **シナリオ**：S2（修正後）、S5
- **何が起きるか**：§2 で「指摘ありはフラグ、元の状態を保つ」。見積中の行の型式を設計が直すと状態は「見積中」のまま。購買が「5 変更あり」を見逃すと、**旧型式の概算見積で選定・正式見積依頼が進む**。数量変更3行も単価ブレークが変わるのに「見積済」のまま。
- **修正案**：
  - 状態機械に **「再見積要」フラグ**を追加：見積中以降の行で `model/mfr/qty/need_date` が変わったら自動で立てる。`qty` は案件設定の許容幅（既定 ±10%）以内なら立てない。
  - 購買側「9 購買作業」ビューの既定フィルタに「再見積要」を含め、`Ctrl+K → 再見積を依頼（n行, m社）` で商社別の差分依頼書を出す（B-13 の概算依頼書と同じ型）。
  - 正式見積依頼中・正式見積済の行が変わった場合は**自動で「選定済」に戻し**、依頼書 Rev を上げる（B-16）。

### B-12 `a` の意味が「最安」（keyboard-spec）と「最高スコア」（flow-design）で矛盾し、一括コマンドは「最安」のまま
- **シナリオ**：S3
- **何が起きるか**：設計者が keyboard-spec 通り `a`＝最安と思って押す／`未採用を最安で一括採用` を実行 → 購買のスコア1位と違う商社が選定済になる → 購買が全行見直し。ステータスバーも「a 採用」のみで区別がつかない。
- **修正案**：`a`＝最高スコア採用に統一し、ステータスバー表記を `a 採用(スコア1位)` にする。パレットの一括コマンドは `未採用をスコア1位で一括採用` に改名、`未採用を最安で一括採用` は残すなら「価格のみ」と明記して要決定行きにする。keyboard-spec 5.4 の `a` の説明を v0.2 で更新（spec 否定ではなく表現の同期）。

### B-13 購買が商社に出す「概算見積依頼書」と、商社からの回答の取り込みが無い（80行×3社＝240セル手入力）
- **シナリオ**：S3
- **何が起きるか**：§5 には正式見積依頼書の生成があるが、**概算見積の依頼書が無い**。購買は `Ctrl+E` の Excel 出力で代用するが、出力は BOM 全列なので他社の単価や社内の採用列が混ざる。回答の取り込みは未決事項1として空欄。240セルを手で打つなら Excel 往復の方が速く、ツールを使わない。
- **修正案**：
  - `Ctrl+K → 概算見積を依頼`：選択行（既定：提出済の全行）× 選択商社で**商社向け依頼 Excel**（列：依頼No・行ID・部品名・型式・メーカ・数量・単位・必要日・備考 ＋ 回答列：単価・納期・MOQ・在庫・代替提案・有効期限、商社名と依頼 Rev をヘッダに固定）を生成。状態を「見積中」に。
  - 取り込み：`Ctrl+K → 見積回答を取り込む` で同じ Excel を貼り付け/ファイル → **依頼No と行 ID で突合**し、商社列に流し込む。突合できない行・型式が違う行は「要確認（購買）」に出す。
  - これにより商社ごとの単価/納期/MOQ/在庫/有効期限が構造化され、スコア計算（B-14）の入力が揃う。

### B-14 スコアの入力値が定義不足で、購買が納得できる順位にならない
- **シナリオ**：S3、S6
- **何が起きるか**：
  - 納期30「案件納期に対する余裕日数」：案件納期が「未定」だと計算不能。行ごとの必要日が無いので、FA で実際に効く「在庫即納」が反映されない。
  - 実績20：商社マスタの実績値は誰がメンテするか未決。新規商社・初取引は0点になり、安くて早くても1位になれない。
  - 条件10「最小ロット・端数・送料」：送料は案件単位、MOQ は行単位で、点数化式が無い。
  - 「スコア拮抗」の閾値が無いので「7 要決定」に何が入るか分からない。
  - 価格40「最安を100、以降は比率」：比率の向き（最安/当該 か 当該/最安 か）が書かれていない。
- **修正案**：
  - 納期：`need_date`（B-04）を基準に `余裕日 = need_date − (今日 + 商社納期)`。在庫品は商社回答の `stock: true` で納期0日扱い。余裕≥0 で100、負なら0、閾値は案件設定。
  - 実績：商社マスタ `otd_rate`（納期遵守率）`defect_rate` を**購買が入荷時 `i` に記録する実績から自動集計**し、データが無い商社は「実績 未評価＝中立50」とし、重みを自動で価格・納期に振り直す。
  - 条件：`MOQ 超過分の金額（端数×単価）` を価格に加算し、条件項目は「MOQ≤数量なら100、超なら 100×数量/MOQ」。送料は案件単位で集約試算にだけ使う。
  - 拮抗閾値：案件設定 `tie_threshold`（既定 5点）。1位と2位の差が閾値以内なら要決定。
  - 価格：`100 × 最安単価 / 当該単価` と明記。
  - 行を `Space` で開いた内訳に「この行だけ重みを変える」（`w` キー → 価格/納期/実績/条件を `←→` で調整）を付け、FA の「この1行は納期優先」を行単位で可能にする。

### B-15 スコア2位以下を選ぶとき、理由の記録と PM 承認の経路が無い
- **シナリオ**：S3（1行だけ2位商社）
- **何が起きるか**：`Shift+A → 2` で2位を採用できるが、RACI では例外は PM が決める。押した瞬間に「選定済」になるのか「要決定」になるのか不明。理由（在庫品で納期が勝つ）を書く場所が無いので、PM は要決定ビューで「なぜ？」と聞き直す。
- **修正案**：
  - `Shift+A` で1位以外を選ぶと、理由入力（`1` 納期 `2` 在庫 `3` 品質/実績 `4` 集約 `5` その他＋本文）を必須にし、状態は「選定済（PM承認待ち）」、「7 要決定」に理由付きで並ぶ。
  - PM 側：要決定ビューで `y`（承認）/ `Shift+N`（差戻し、理由必須）。承認でイベントログに `approved_by` が残る（医療・自動車の変更記録に流用）。
  - 案件設定で「例外承認を不要にする（金額差 < X 円 または < Y%）」の閾値を持ち、小額の例外で PM を止めない。

### B-16 正式見積で差分超過のとき、PM が否とした後の遷移が無い
- **シナリオ**：S4（+15% が3行）
- **何が起きるか**：差分閾値が未定義（15%が超過か分からない）。PM が「受入れない」と決めた後、状態機械には「正式見積済 → 選定済」に戻る遷移が無い。購買は再交渉するのか、2位商社に正式見積を出すのか、設計に代替を頼むのかが決まらず止まる。2位商社に出す場合、依頼書の「選定理由（スコア内訳）」が自動で「スコア2位」と出て、商社に見せられない。
- **修正案**：
  - 案件設定 `formal_diff_threshold`（既定 ±10%、金額絶対値 X 円でも可）。
  - 要決定の行で PM の選択肢を1キーで：`y` 受入れ / `2` 再交渉（購買へ、状態「正式見積中（再交渉）」）/ `3` 次点商社へ（状態「選定済」に戻し、次点を自動選定、依頼書 Rev+1）/ `4` 設計へ代替依頼（指摘「代替提案依頼」を設計に起票）。
  - 正式見積回答の入力項目：`formal_unit_price` `formal_lead_time` `valid_until` `diff_reason`（数量/為替/MOQ/仕様変更/その他）`payment_terms`。**概算と正式を別列で保持**し上書きしない。
  - 依頼書の「選定理由」は社内記録と商社向けを分け、商社向けは「貴社を選定しました」＋条件のみ。スコア内訳は社内 PDF にだけ付ける。

### B-17 正式見積依頼書に Rev・有効期限・案件情報が無く、見積中の変更で商社と食い違う
- **シナリオ**：S4、S5、S6
- **何が起きるか**：依頼書は「商社ごとに生成」とだけあり、同じ商社に2回目を出したとき商社は「前の依頼とどこが違うか」を聞き直す。有効期限が無いので S6 の前倒しで「その単価はまだ有効か」の確認が発生する。
- **修正案**：依頼書ヘッダに `案件ID / 依頼No（案件-商社-Rev）/ 発行日 / 回答期限 / 必要納期 / 納入先 / 支払条件 / 通貨`。Rev+1 のときは**差分行だけに「変更」マークと旧値**を付けた差分シートを自動添付。回答側に `valid_until` を必須にし、期限が切れた行はランプ（警告）に出す。

### B-18 設計変更の承認者がおらず、見積中の変更が無条件で流れる
- **シナリオ**：S5
- **何が起きるか**：RACI に「設計変更」の行が無い。設計が型式5行・数量3行を変えると購買には「5 変更あり」に出るが、**変更理由も、PM が承認したかも分からない**。自動車・医療では承認無しの変更は即 NG。購買は「これは確定ですか？」と聞き直す。
- **修正案**：
  - 提出済以降の行を設計が編集すると `change_reason`（設計都合/購買指摘対応/客先要求/コスト/納期）を必須入力。購買指摘対応以外は **PM の承認待ち**（案件設定でオフにできる）。
  - RACI に追加：「提出後の設計変更：決める人＝設計、承認＝PM（金額影響 > X またはスケジュール影響）、相談＝購買」。
  - Rev 単位の変更一覧（B-03）に理由・承認者を含めて Excel の「変更点」シートにも出す。

### B-19 `Ctrl+Z` が他人の操作まで戻せる（イベントログ共通）
- **シナリオ**：S2、S5
- **何が起きるか**：「どの操作も `Ctrl+Z` で戻せる」とイベントログ共通が組み合わさると、設計の `Ctrl+Z` が直前の購買の単価入力を戻す。気づかないまま進み、購買は「入れたはずの単価が消えた」と聞き直す。
- **修正案**：`Ctrl+Z` は**自分の操作だけ**を戻す（イベントログに `actor` を持ち、自分の直前イベントを逆適用）。他人の変更は「履歴」から「この変更を取り消す」として明示操作にし、相手に通知する。

### B-20 案件納期の変更操作が無く、前倒し後に何が NG かを抽出できない
- **シナリオ**：S6
- **何が起きるか**：納期は新規 BOM ガイドで入れるが、**後から変える操作が定義されていない**。変えたとしても納期30のスコアが全行再計算され、選定済80行の順位が入れ替わる。全部「7 要決定」に入ると PM は判断できず、購買に「どれが間に合わないか出して」と口頭で頼む。
- **修正案**：
  - `Ctrl+K → 案件納期を変更`（PM のみ、理由必須、イベントログに記録）。変更時に**影響サマリ**を即時表示：「新納期に間に合わない行 7 / 商社変更で間に合う行 4 / 特急費用で間に合う行 2 / 不可 1」。
  - 選定済の行は自動では覆さず、`need_date` を過ぎる行だけ「納期NG」フラグで要決定に出す。PM は行ごとに `y` 商社変更を承認 / `2` 特急費用承認（費用上限入力）/ `3` 設計へ代替依頼 / `4` 納期を個別に許容。
  - 正式見積依頼中の行は B-17 の Rev+1 で商社に納期変更を再依頼。発注済の行は「納期短縮依頼」として購買の別フラグ。

### B-21 「見積済」「選定済」の成立条件が無く、3社中1社未回答の行をどう扱うか決まらない
- **シナリオ**：S3
- **何が起きるか**：3社に依頼して2社回答の行で `a` を押してよいのか、「見積済 38/80」の 38 は何を数えるのかが不明。購買は「残り1社を待つか」設計に聞くか自分で決めるか止まる。
- **修正案**：案件設定 `quote_complete_rule`：「全社回答」/「n社以上回答」/「回答期限到達で締め」。期限到達時に未回答の商社は「未回答（辞退扱い）」で自動確定し、スコア計算から除外。行を `Space` で開いた内訳に未回答商社を灰色で出す。

## 3. あいまいで聞き直しが発生する箇所（AMBIGUOUS）

### A-01 「要確認」ビュー（4）が設計向けなのに、購買側の要確認（取込み不一致、未回答、有効期限切れ）の置き場が無い
- **シナリオ**：S3、S4
- **何が起きるか**：購買側の「自分がやるべきこと」が一覧できず、ランプの件数も設計向け。
- **修正案**：「4 要確認」を役割で自動フィルタ（ログイン役割が購買なら購買起票以外・購買宛を既定表示）。ヘッダーランプも役割別の件数にする。

### A-02 RACI の「期限の目安」の起点と、超過したときに誰のランプが変わるか
- **シナリオ**：S3（見積済から2営業日）、S4（回答から1営業日）
- **何が起きるか**：「見積済」の時刻が行ごとに違うので案件としての期限が分からない。超過してもランプの色が変わるだけで**誰の**ランプか不明。
- **修正案**：行に `state_changed_at` を持ち、期限は行ごと。ヘッダーランプを「自分宛の期限超過 n件」にし、`n` で飛べる。案件一覧（B-02）にも出す。

### A-03 「商社を集約」の試算後、どのキーで集約を適用し、誰が承認するか
- **シナリオ**：S3
- **修正案**：試算パネルで `Enter` → 「集約案で全行を選定（PM承認待ち）」。総額差が閾値超なら要決定へ。試算は「1社」だけでなく「2社まで」の組合せも出す（FA/民生では2社集約が現実的）。

### A-04 指摘種別が固定7種で、「ルールを追加」との対応関係が無い
- **シナリオ**：S2
- **何が起きるか**：「型式あいまい」をルール化するには具体的な判定（例：末尾のサフィックス欠落、全角/半角混在、メーカ型式表記と不一致）が要るが、誰が何を書けばルールになるか不明。購買が追加するのか設計が追加するのかも不明。
- **修正案**：ルール定義を「対象列 × 判定（正規表現/必須/候補リスト/メーカ型式マスタ照合）× 重大度」とし、指摘を「確認済」にする時に `Ctrl+.` で「この指摘からルールを作る」を出す（起票者=購買が作れる）。ルールは全案件共通なので `owner` と `enabled` を持ち、誤検知が多いルールは購買が無効化できる。

### A-05 「購買提出用」ビュー（2）の列と「Excel 出力」が商社に見せてよい情報か
- **シナリオ**：S1、S3
- **何が起きるか**：購買が商社向けに流用すると他社価格・社内採用情報が漏れる恐れ。
- **修正案**：出力先を `1 社内` `2 商社向け（価格列を除外、依頼商社の列のみ）` `3 保管用（全列）` から選ぶ。

### A-06 調達区分（支給/客先指定）の行が状態機械と相見積の対象外になるか
- **シナリオ**：S1
- **修正案**：`proc_type` が 支給/客先指定/社内在庫 の行は「見積対象外」とし、購買作業ビューから除外、ヘッダー集計の分母からも外す。客先指定でも単価だけ要る場合は「指定商社のみ見積」。

### A-07 通貨・税・単価の桁（円未満）・金額＝単価×数量の定義
- **シナリオ**：S3、S4
- **修正案**：案件に `currency`、商社回答に `unit_price`（小数2桁）と `tax_included`。表の「金額」は税抜 `unit_price × qty`（MOQ 超過分を含むかは `c` で列を分ける）。

### A-08 送付先（購買担当）が1人固定で、複数購買担当や担当交代の扱い
- **シナリオ**：S1、S6
- **修正案**：案件の `buyers[]`（主担当＋副）。インボックスは主担当に出るが副も見られる。

### A-09 スコアの重みを「案件ごとに設定」するのは誰か
- **シナリオ**：S3
- **修正案**：既定は購買マスタ（業界/製品種別ごとのプリセット）。案件での上書きは購買、PM 承認不要。変更はイベントログに残す。

### A-10 発注済・入荷済の行への指摘・変更の可否
- **シナリオ**：S5、S6
- **修正案**：発注済以降は設計が型式・数量を編集できない（ロック）。変更したい場合は「発注後変更依頼」を購買に起票し、購買がキャンセル可否を判断。

### A-11 「要決定」に入った行を PM が決めるまで、設計・購買がその行を触れるか
- **シナリオ**：S3、S4、S6
- **修正案**：要決定中は選定・依頼の操作をブロック（ステータスバーに「PM判断待ち」）。データの編集は可。

### A-12 長納期部品の先行手配（LTB）の判断がフローに無い
- **シナリオ**：S6（前倒し）、半導体装置・建築設備
- **修正案**：商社回答の `lead_time` が `need_date` を超える行は見積済の時点で「要決定（先行手配）」に出し、PM が「正式見積を待たず発注」を承認できる（状態「見積済 → 発注済」の直接遷移を承認付きで許可）。

## 4. 良い点（短く）

- 指摘を「行ID＋セル」の構造化データにし、再提出ボタンを無くした発想は正しい。これが実現すれば目標2の大半は達成できる。
- 状態を**行ごと**にし、案件状態を集計にしたのは購買の実務（行ごとに進み方が違う）に合う。
- スコアの内訳を `Space` で開いて見られる「透明な加重平均」は、商社への説明責任を果たしやすい。
- 同じ指摘を `ルールを追加` で提出前チェックに回す仕組みは、指摘の再発ゼロに直結する。
- RACI を文書に持ち込んだこと自体は良い（ただし行が足りない）。
- 通知をアプリ内ランプに絞り、メールを送らない方針は、購買側のメール地獄を増やさない。
