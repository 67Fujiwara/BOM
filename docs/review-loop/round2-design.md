## 2. 新規 BLOCKING（v2 で導入した仕組みが生むもの）

### N1. 設計が「新しいBOM」で入れる納期が PM の列であり、社内工程日数・予算・見積完了条件の入力者と時期が無い
- **シナリオ**：S1
- **何が起きるか**：§1 の権限表で「案件納期・予算・重み確定」は PM だけが書ける。一方、新規BOMガイド（keyboard-spec 7.1 手順3、§13 で手順4・5 だけ改名）では設計が納期を入れる。さらに 必要日＝納期−社内工程日数 の「社内工程日数」、予算、見積完了条件、回答期限、各閾値は `Ctrl+K → 案件設定`（PM のみ）にしか無く、PM が開くまで 必要日＝納期（工程日数 0）で計算される。設計は提出前に「必要日 あと M 日」が間違っていることに気づき、PM に「工程日数を入れてください」と頼む。PM が入れるまで 納期スコア・先行手配の判断が全部ずれる。
- **修正案**：新規BOMガイドに「社内工程日数（案件種別のプリセットから既定）」「予算（任意）」を追加し、設計が入れた 納期・工程日数・予算 は「仮（PM未確定）」バッジで保存。PM の `案件設定` で確定（確定イベント）。ヘッダーの必要日に「仮」を表示。§1 の権限表を「初期値は作成者、確定と変更は PM」に直す。

### N2. 指摘対応の型式・メーカ修正が無条件に「再見積要」になり、取得済み見積が消える
- **シナリオ**：S2（型式あいまい5・メーカ未記入3）
- **何が起きるか**：§4「型式・メーカが変わったときだけ状態が提出済（再見積要）に戻り、既存見積は灰色」。購買が「-A か -B か？」と聞くのは見積の最中で、商社はすでに正しい方で回答済みのことが多い。設計がサフィックスを足して公開した瞬間に 8 行が再見積要になり、購買は商社へ再依頼するか、設計に「据え置きでいいよね」と聞く。§6.3 は「マイナー修正と置換は別」と書くが、§4 の遷移規則にはその区別が無い。
- **修正案**：公開する変更が **指摘対応（種別 型式あいまい / メーカ未記入）** のときは自動で再見積要にせず、`r` と同じく「要再確認」フラグを付けて購買の `5` で `Enter` → `1 据え置き / 2 再見積` を選ばせる（§6.3 の `r` の仕組みを流用）。指摘対応でない変更セットの型式/メーカ変更だけが自動で再見積要。§4 にこの例外を明記。

### N3. 廃番・代替提案の「提案を適用」で、提案に書いた単価・納期・商社が新行の見積に流れない
- **シナリオ**：S2（廃番2）、S4（`4` 設計へ代替依頼）
- **何が起きるか**：§6.1 の提案は `{型式, メーカ, 商社, 単価, 納期, MOQ}` を持ち、購買がここに入れる。§6.3 の `r` は「指摘・相見積・状態を新行にコピー」= **旧部品の見積** をコピーする。提案の単価・納期は新行の商社列に入らず、購買は自分が指摘に書いた値を商社列にもう一度打つ（転記）。§6.2「廃番：価格差が閾値超なら PM」の価格差も、提案単価が商社列に無いと計算できない。
- **修正案**：「提案を適用」で新行を作るとき、提案の 商社 列に 単価・納期・MOQ を「概算（出典 I-0xx）」として書き込み、旧部品の見積は灰色の履歴に落とす。価格差＝提案単価 − 旧行の採用単価 で閾値判定し、超なら自動で `7`。

### N4. ボール表に「見積済（選定待ち）」「回答済の指摘」「代替承認待ち」が無く、選定の番が設計に届かない
- **シナリオ**：S3（B6 の残りも同根）
- **何が起きるか**：§2 ボール表は「提出済・見積中・再見積要・選定済(正式依頼前)・正式依頼中・正式見積済→購買」「下書き・指摘あり(未対応)…→設計」「PM承認待ち…→PM」。**見積済** がどこにも無い。見積済になった行は誰のボールでもなく、設計の受信箱に「自分宛」として出ず、設計の `4`（自分宛の指摘・チェックNG）にも出ない。選定期限（見積済から2営業日）は静かに過ぎ、購買が「選んでください」と連絡する。設計が `Shift+Enter` で回答した指摘（回答済）も、購買のボールとして表に無い。
- **修正案**：ボール表に「見積済（未選定）→ 選定者」「指摘 回答済 / 対応済（未確認）→ 起票者」「代替承認待ち → 設計（客先承認の記録）」を追加。設計の `4` のフィルタを「自分宛の指摘・チェックNG **・ボール＝自分の行**」に広げ、ステータスバーに `選定待ち 60`。受信箱の「自分宛」はボールから数える、と §2 に明記。

### N5. 「再見積要」のボールが矛盾し、状態名も §4 と §9.1 で違う
- **シナリオ**：S5（型式変更5行）
- **何が起きるか**：§2 ボール表は「再見積要の原因が設計 → 設計」と「再見積要 → 購買」の両方を持つ。設計が型式を変えて公開した行は「原因が設計」なので設計のボールになるが、設計にはもうやることが無い（再依頼は購買の仕事）。設計と購買が互いに相手待ちで止まる。また状態名が §4 では「提出済（再見積要）」、§9.1 では「選定済（再見積要）」、§4 の図では「再見積要」単独で、`9 購買作業` のフィルタ（提出済/見積中/見積済/再見積要）にどれが入るか分からない。
- **修正案**：「再見積要」は **フラグ** にして、元の状態（提出済 / 選定済 / 正式依頼中）を保ったまま付ける。ボールは一律 **購買**（再依頼または据え置き判断）。「原因が設計」の行は削除し、設計に戻すのは `Shift+Y` 差戻しだけにする。§4 の図と §9.1 の表記を揃える。

### N6. 調達区分＝指定商社 のとき、どの商社かを書く列が無い
- **シナリオ**：S1
- **何が起きるか**：§3.1 の調達区分に `指定商社` があり、§3.1「指定商社は1社のみに依頼」「選定済（固定）」と動くが、商社名を入れる列が無い。設計は備考に書き、購買は「どこですか」と聞くか備考を読んで転記する。
- **修正案**：列 `指定先`（商社マスタから選択、調達区分＝指定商社 / 客先指定品のとき必須。§12 の必須ルールに追加）。`概算見積を依頼` はこの列の商社だけに依頼し、`選定済（固定）` の採用商社にもこの値を使う。

### N7. `7` ビュー内のビュー切替 `Ctrl+1`〜`Ctrl+9` がブラウザ予約キー（keyboard-spec 基本方針 6 違反）
- **シナリオ**：S4・S6（PM の操作。設計・購買間の手戻りではないが仕様の自己矛盾）
- **何が起きるか**：`Ctrl+1`〜`Ctrl+8` は Chrome / Edge / Firefox のタブ切替、`Ctrl+9` は最後のタブ。keyboard-spec §2-6「ブラウザ予約キーは使わない」に反し、PM が `7` から `1` に戻ろうとしてブラウザのタブが切り替わる。macOS では `Cmd+数字` で奪えない。
- **修正案**：`7` ビューの PM 対策キーを数字から文字に変える（`y` 承認、`Shift+Y` 却下、`b` 次点(backup)、`g` 再交渉、`d` 設計へ代替依頼、`q` 数量見直し、`e` 特急/分納、`l` 先行発注(LTB)）。これでビュー切替の `1`〜`9` は全ビューで共通のまま。§13 の該当行を差し替え。

### N8. 一括採用で「拮抗」の行が PM の `7` に載る（単行では設計の裁量なのに）
- **シナリオ**：S3
- **何が起きるか**：§8.2 単行：拮抗閾値以内は設計の裁量で確定。§8.2 一括：「拮抗・承認要の行は仮採用で `7` へ」。60 行一括すると拮抗の 15 行が PM の要決定に載り、PM は「なぜこれを私が決めるのか」と設計に聞く。設計は一括を避けて 1 行ずつ `a` を押す。
- **修正案**：一括採用では「拮抗」行は推奨で確定し、`拮抗` バッジを付けて **設計の `4`**（ボール＝設計、期限は選定期限と同じ）に「見直し推奨」として出す。`7` に載せるのは単行と同じ「承認要（閾値超）」だけ。パレットの実行結果に `採用 45 / 拮抗 15（要見直し）/ 承認要 0 / 見積中スキップ 20` を出す。

## 3. 新規 AMBIGUOUS

### M1. 「重みは提出時に PM が確定」が提出・選定をブロックするのか
- **シナリオ**：S1、S3
- **何が起きるか**：§8.1「案件での上書きは購買、提出時に PM が確定（既定のままでも可）」。`Ctrl+Enter` を押したとき PM の確定を待って提出済にならないのか、提出は通って PM に「重み確認」が `7` に載るだけなのか不明。後者なら、PM が未確定のまま見積済になった行に `a` を押してよいかも不明。
- **修正案**：提出は PM を待たない。提出時に `7` に「重み確認（案件）」が1件載り、未確認でも選定可。未確認のまま選定した行は §8.1 のスナップショットで固定され、後の確定は §9.2 の影響試算を通る、と明記。

### M2. 必要数を変えたとき発注数（購買の列、既定＝必要数）が追従するか
- **シナリオ**：S5（数量変更3行）
- **何が起きるか**：購買が MOQ で丸めた発注数が入った後に設計が必要数を変えると、発注数が古いままか、既定に戻るかが不明。購買は 20% 以内の変更（再見積要にならない）に気づかず古い数量で発注しかねず、設計に「発注数は変えていい？」と聞く。
- **修正案**：必要数の公開で発注数を「新必要数を MOQ・入数で丸めた値」に再計算し、購買が手で変えていた場合は `発注数 要確認` フラグを付けて購買の `4` に出す。

### M3. 必要日(行) が絶対日か「案件必要日からの相対日数」か
- **シナリオ**：S6
- **何が起きるか**：設計が先行手配品 5 行に必要日(行) を日付で入れた後、PM が納期を前倒しすると、案件必要日は動くが行の日付は動かない。前倒し幅が大きいと行の必要日が案件必要日より **後** になり、影響試算で納期NG から漏れる。PM は設計に「5 行も直して」と頼む。
- **修正案**：必要日(行) は「案件必要日の n 日前」として保持（表示は日付）。絶対日で固定したい行は `固定` チェック。影響試算に「行の必要日を再計算 n 行」を出す。

### M4. `Shift+Enter` が3つの意味を持ち、文脈の定義が無い
- **シナリオ**：S2、S5
- **何が起きるか**：keyboard-spec 5.3 `Shift+Enter`＝下に行を追加して部品名の編集。v2 §13 は「（指摘上）直さず回答」、§9 は「`7` ビューでコメント付き承認」。設計が `4` 要確認ビューで指摘の付いたセルにいるとき、S5 の追加行を作ろうと `Shift+Enter` を押すと回答ダイアログが開く。「指摘上」がセルなのか、`Space` で開いた指摘パネル内なのかも不明。
- **修正案**：`Shift+Enter` は行追加のまま。「直さず回答」は `Space` で開いた指摘パネル内の `Enter`（または `Shift+R` の返信種別「回答」）、PM のコメント付き承認は `Shift+Y`/`y` の後に理由入力欄で `Tab`、と文脈を1つに決める。

### M5. `Shift+X` が購買＝起票者のとき「差戻し」か「見送り」か
- **シナリオ**：S2
- **何が起きるか**：§13「`Shift+X`：差戻し（購買）/ 見送り（起票者・PM）」。通常は購買が起票者なので両方の条件を満たす。
- **修正案**：`Shift+X` → `1 差戻し（理由）/ 2 見送り（理由）` の 2 択を出す。

### M6. `[` `]` が `5` ビューでは Rev 切替になり、ナビの分類移動と衝突する
- **シナリオ**：S2、S5
- **何が起きるか**：keyboard-spec 5.2 `[` `]`＝前の分類/次の分類。v2 §5 では `5 変更あり` で Rev 切替。`5` で分類ジャンプができない。
- **修正案**：Rev 切替は `<` `>`（`Shift+,` `Shift+.`）か、`5` ビュー上部の Rev セレクタに `Tab` でフォーカス。

### M7. 設計が起票した「質問」の発行タイミング
- **シナリオ**：S2、S3
- **何が起きるか**：§6.3「起票した指摘は下書き。`Ctrl+Enter`（購買）で一括発行」。設計の `Ctrl+Enter` は「提出/公開」。設計が質問（設計→購買）を書いた後、`Ctrl+Enter` で行の公開と一緒に発行されるのか、質問だけ下書きのまま残るのかが不明。残ると購買に届かず、設計は「返事が来ない」と思う。
- **修正案**：`Ctrl+Enter` は役割に関係なく「自分の未公開の行 ＋ 自分の下書き指摘」をまとめて発行し、確認に `行 5 / 指摘 1 を公開` と出す。ステータスバーの `未公開 n 行` に `指摘 m` を併記。

### M8. `a` と一括採用を「見積中（回答 2/3）」の行に押したときの扱い
- **シナリオ**：S3
- **何が起きるか**：状態機械は 見積済 → 選定済 だが、見積中でもスコアは 2 社分で計算・表示される。`a` が効くなら 3 社目の回答前に採用して購買に止められる。効かないなら、一括で何行がスキップされたか分からず期限超過になる。
- **修正案**：`a` は見積済のみ。見積中では灰色＋ステータスバー `回答 2/3 待ち`。例外として `Alt+A`/`Shift+A` は見積中でも「先行採用（理由必須、§4 の先行発注と同じ PM 許可が要る）」。一括は結果サマリにスキップ数を出す（N8 と同じ）。

### M9. 正式見積の差分閾値「¥X」の既定値が未記入
- **シナリオ**：S4
- **何が起きるか**：§9.1「既定 ±10% または ¥X の大きい方」。X が無いと案件設定で必ず聞かれ、PM が購買に「いくらにする？」と聞く。
- **修正案**：既定 ¥10,000（§8.2 の例外閾値と同じ値）と書く。

### M10. `5 変更あり` の既定が Rev 単位で、小刻みな公開で Rev が増える
- **シナリオ**：S2
- **何が起きるか**：設計が 12 件を 1 件ずつ `Enter` → `Ctrl+Enter` すると Rev が 12 個できる（受け入れ基準は最後に 1 回を想定しているが、仕様は止めていない）。購買は `[` `]` で 12 回切り替えて差分を見る。
- **修正案**：`5` の既定は「自分が未確認の差分すべて（Rev 横断、起因列つき）」。Rev 切替はフィルタ。あわせて、同じ日の連続公開を 1 Rev にまとめるか、公開時に「直前の Rev に追記 / 新しい Rev」を選べるようにする。
