## 2. 新規 BLOCKING（v2 で入った仕組みが生む矛盾・抜け）

### NB1. 納期NG 対策「商社変更」（購買）と、採用列の書き込み権限（選定者＝設計）が矛盾する
- シナリオ：S6（S4 の `3` 再交渉後に商社を変える場合も同じ）
- 何が起きるか：§9.2 で PM が納期NG 行に対策区分「商社変更」を割り当てると購買の受信箱に出るが、§1 の権限表では **採用（選定）列は選定者（既定：設計）しか書けない**。購買は `Shift+A` を押しても「権限なし」で止まり、設計に「採用を変えて」と頼む → 設計は理由を知らない → 聞き直し。PM の `2` 次点商社へ は自動選定なので動くが、購買が商社を選び直す経路が無い。
- 修正案：対策区分「商社変更」を割り当てた行は、**その行だけ採用列の書き込み権限を購買に委譲**（決定イベントに「委譲」として記録、`Shift+A` の理由は `1 納期` を自動記入）。または対策区分を「次点へ（自動）」「購買が再選定（委譲）」「設計が再選定」に分け、PM が割り当てる時点で権限が決まるようにする。

### NB2. 行の必要日（先行手配品）が絶対日付のままで、案件納期の前倒しに追従しない
- シナリオ：S6
- 何が起きるか：§3.1 「必要日（行）：空なら案件の必要日を継承。先行手配品はここで前倒し」。設計が旧納期を基準に「必要日＝旧必要日−14日」と絶対日付で入れていると、PM が案件納期を前倒ししても **その行の必要日は動かず、影響試算にも納期NG にも出ない**。前倒し後に最も危ない先行手配品が検知から漏れ、組立直前に発覚する。
- 修正案：必要日（行）は **「案件必要日からの前倒し日数」**（例：−14）で保持し、表示は日付に展開する。絶対日付で入れたい行（客先指定の納入日）は `固定` 属性を付け、影響試算で「固定必要日の行 k 件」を列挙して PM に再確認を求める。

### NB3. 変更セットが PM に却下されたときの公開値の扱いと、指摘対応と設計変更が混ざった公開の扱いが無い
- シナリオ：S5（医療・自動車の既定＝PM承認 ON）
- 何が起きるか：§5 では公開時に変更理由を聞き「PM承認待ち」で `7` に載せ、購買には「承認待ちの変更あり」だけ見える。(1) PM が `Shift+Y` で却下したとき、値は作業中（未公開）に戻るのか、公開済のまま却下フラグだけ付くのかが無い。後者だと購買が既に再見積を出しており二度手間。(2) 同じ `Ctrl+Enter` に **指摘対応 7 行＋設計変更 3 行** が混ざった場合、指摘対応分は即時反映（§5「公開した瞬間に対応済」）、設計変更分は承認待ちで、1 回の公開が半分だけ購買に届く。購買は「残りはどこ」と聞く。
- 修正案：却下は **公開を取り消して作業中に戻す**（Rev は「却下」として履歴に残す）と明記。公開時に指摘対応と設計変更が混ざっていたら、**自動で 2 つの Rev に分割**（Rev.4 指摘対応＝即時、Rev.5 変更セット＝承認待ち）し、ステータスバーに「Rev.5 PM承認待ち 3 行」を出す。

### NB4. `Shift+X` が購買にとって「差戻し」と「見送り」の両方になる
- シナリオ：S2
- 何が起きるか：§6.3・§13 で `Shift+X` は「差戻し（購買）/ 見送り（起票者・PM）」。通常、起票者＝購買なので、購買が押したときにどちらになるか決まらない。差戻しのつもりで見送り（クローズ）になると設計には届かず、指摘が消えたまま提出が進む → 後工程で再発。
- 修正案：`Shift+X` は **差戻し専用**。見送りは `Ctrl+.` の候補「見送りにする（理由）」または パレット `<指摘ID> 見送り` に分ける。ステータスバーの文脈表示に「Shift+X 差戻し」とだけ出す。

## 3. 新規 AMBIGUOUS

### NA1. `7 要決定` のキーが、載った理由（例外選定 / 差分超過 / 納期NG / 変更セット / 2回目差戻し / 案件レベル）ごとにどれが有効か決まっていない
- シナリオ：S2, S3, S4
- 何が起きるか：例外選定の承認待ち行で `2` 次点商社へ を押すと「次点」は設計が選んだ 2 位なのか 3 位なのか不明。2回目差戻しの指摘に `y` を押すと購買側の主張を承認なのか設計側なのか不明。`Shift+Y` は「見積済に戻し設計へ」固定だが変更セットの却下には合わない。
- 修正案：要決定種別 × 有効キー × 遷移先 の対応表を §9 に置き、無効なキーはステータスバーで灰色。2回目差戻しは `y` = 購買の指摘を支持（設計に戻す）/ `Shift+Y` = 設計の回答を支持（指摘を確認済に）と定義する。

### NA2. 「提出時に PM が重みを確定」の仕組みと、未確定のまま見積済になったときの扱い
- シナリオ：S1, S3
- 何が起きるか：§8.1 は時期だけで、`7` に「重み確定」が載るのか、確定前に設計が `a` を押せるのかが無い。確定前に選定するとスナップショットは未確定の重みで固定され、後から PM が「その重みじゃない」と言っても覆せない。
- 修正案：提出 Rev.1 で案件レベルの要決定「重み確定（既定で OK なら `y`）」を `7` に自動で載せ、未確定のうちは `a` は「仮採用」（スナップショット無し）で、確定時に再計算してから固定する。

### NA3. 正式見積の受入で「PM の上」の決裁が必要になる条件
- シナリオ：S4
- 何が起きるか：§10 で正式見積の受入の A が「PM の上（ツール外決裁を記録）」。+15% の 3 行が ¥3,000 でも決裁を取りに行くのか、案件予算超過のときだけなのかが無い。PM が毎回社内規程を確認する。
- 修正案：案件設定に `上長決裁の条件`（行の差額 ≥ ¥X、または案件総額が予算比 +n%）を持ち、該当する決定だけ `Shift+Enter` のツール外決裁欄を必須にする。

### NA4. 「メーカ指定＝任意」の行と、「メーカ未記入はエラー（提出ブロック）」の整合
- シナリオ：S1
- 何が起きるか：§3.1 のメーカ指定 `任意` は「どのメーカでもよい」の意味なのに、§12 でメーカ未記入はエラー。設計はダミーのメーカを入れて提出し、購買はそのメーカで見積を取ってしまう。
- 修正案：メーカ指定＝任意 の行はメーカ必須ルールを警告に落とし、購買が見積依頼 Excel の「代替提案」列でメーカを埋める運用を明記する。

### NA5. 購買の未発行の指摘が見える場所
- シナリオ：S2
- 何が起きるか：指摘は下書き → `Ctrl+Enter` で発行。設計側のステータスバーには `未公開 7 行` が出るが、購買側に「未発行の指摘 n 件」が無い。購買は発行したつもりで設計に届いていない。
- 修正案：購買のステータスバーに `未発行 12 件`、`9 購買作業` ビューのヘッダーにも同じ件数を出す。案件を閉じるときに未発行があれば確認。

### NA6. 影響試算の「推奨が変わる行 m」に対して確定後に何もしない
- シナリオ：S6
- 何が起きるか：§9.2 は確定後「選定済は覆さず、必要日を過ぎる行だけ納期NG」。m 行は数字として見えるだけで操作が無く、PM は「見直したいならどうする？」を設計に口頭で頼む。
- 修正案：確定ダイアログに「推奨が変わる m 行を `7` に再選定提案として載せる（任意）」のチェックを置き、載せた行は PM の `y` で選定者のボールへ、`Shift+Y` で現状維持。

### NA7. 納期スコアの基準日「今日」
- シナリオ：S3
- 何が起きるか：§8.1 `余裕日 = 必要日 − (今日 + 商社納期)`。見積済から 2 営業日の間に「今日」が進み、購買が見た推奨と設計が見た推奨が入れ替わることがある。
- 修正案：基準日は **見積済になった日時**（§4 で記録済み）に固定し、選定時に基準日が 5 営業日以上古ければ警告を出す。
