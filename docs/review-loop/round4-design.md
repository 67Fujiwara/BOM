## 3. 新規 AMBIGUOUS

### A17. 先行発注許可のキーが §4 では `l`、§9.1・§16 では `y`、§14 では決定パネルに `l` が残っている
- **シナリオ**：S6（先行発注判断）
- **何が起きるか**：§4 フラグ表「先行発注判断：外れる条件＝PM の `l` 許可 / `Shift+Y`」、§9.1「許可（`y` のみ。`l` は使わない）」、§14 `Enter`（`7`）の選択肢に `l` が列挙。実装者がどちらを配線するか迷う。
- **修正案**：§4 を「PM の `y` 許可 / `Shift+Y`」に、§14 の選択肢から `l` を外す。

### A18. 発注済の行に `d`（設計が代替品検討）が割り当てられた後、設計列ロックの下でどう置換するか
- **シナリオ**：S6（納期NG（発注済）→ `d`）
- **何が起きるか**：§4「発注済以降は設計列をロック。変えたい場合は発注後変更依頼を購買へ起票」、§9.1「発注取消は購買が判断し『発注後変更依頼』」。設計が代替を見つけたとき、ロックされた行に `r`（元行を置換済にする＝行の状態を変える）が効くのか、`Shift+I` `h` で提案欄に代替を書いて購買に投げ、購買が取消した後に誰が新行を作るのかが読めない。発注後変更依頼が承認された後の行の遷移（発注済 → 取消？ 置換済？）も §4 の直列には無い。
- **修正案**：発注済の行でも `r` は有効（元行は「発注済・置換予定」フラグで残り、発注後変更依頼を購買へ自動起票。購買が `取消` を確定した時点で元行を置換済に、新行は下書き → 提出）。§4 のフラグ表に「置換予定」を 1 行追加。

### A19. 「代替承認待ち」が付く条件が「代替提案を適用」に限定され、廃番の提案適用と設計自身の `r` で付くか読めない
- **シナリオ**：S2（廃番 2）、S5（客先承認要の行の型式変更）
- **何が起きるか**：§4「代替可否＝客先承認要 の行に **代替提案** を適用」、§6.2 の A 列も 代替提案 の行だけ。廃番（`提案を適用` は同じ操作）や、設計が自分で `r` した置換でも客先承認は要るが、フラグが付くかが二通りに読める。付かないと承認未取得のまま正式見積・発注に進み、後で客先に止められる（FA・プラント・医療）。
- **修正案**：条件を「代替可否＝客先承認要 の行で、正規化後の型式またはメーカが変わる置換・提案適用・変更セットすべて」に広げる。

### A20. 先行採用（`Shift+A` で商社を選んだ）の承認で、選んだ商社が保たれるか「推奨商社」に置き換わるか
- **シナリオ**：S6（前倒しで長納期品を先行採用）
- **何が起きるか**：§9.1「先行採用 / 先行発注判断」を 1 行にまとめ、`y` →「見積済の行は **推奨商社で** 選定済にしてから発注可」。先行採用は §8.2 で見積中の行に `Shift+A` で商社を **選んで** 理由を書く操作なので、承認時に推奨（最高スコア、しかも見積中で未確定）へ置き換わるのか、選んだ商社のままなのかが読めない。
- **修正案**：行を分ける。先行採用：`y` → 選んだ商社で選定済（先行）。先行発注判断（自動フラグ）：`y` → 推奨商社で選定済（先行）、選定者が `Shift+A` で変えてよい。
